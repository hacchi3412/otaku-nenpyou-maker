# オタク年表メーカー 仕様書

自分がハマってきたものを年別に入力すると、1枚の年表画像を生成できるWebアプリ。生成した画像はXなどでシェアできる。

---

## 1. コンセプト

- 自分が今まで熱中してきたもの（作品・アイドル・趣味など）を年ごとに記録し、1枚の年表画像として可視化する
- 完成した画像はSNS（X）にシェアできる
- 簡単な作りで低コスト運用（サーバー不要、フロントエンドのみで完結）

## 3. データ仕様

### 3.1 年の範囲

- デフォルトで直近10年分を表示
- 「＋もっと過去の年を追加する」ボタンで、過去方向にどんどん年を追加できる
- 終了年（＝現在）は固定。開始年をユーザーに最初に入力させる負担は避ける

### 3.2 空欄の年の扱い

- **先頭側（一番古い側）の空欄**：年表画像から除外する（ノイズ削減）
- **途中の空欄**：そのまま表示する（時間軸の連続性を保つため）

### 3.3 1年あたりの項目数

- 最大3項目まで
- **複数年に渡って続く項目も、開始年〜終了年の範囲内にある各年でこの3枠のうち1つを使う**（別枠ではない）
  - 例：3年続く項目を1件登録すると、その3年それぞれで枠を1つずつ使う
  - 範囲内のどこか1年でも上限（3件）に達している場合、その登録・編集は全体を行わない（詳細は3.6参照）

### 3.4 各項目のデータ

| フィールド               | 必須/任意 | 文字数上限     | 備考                                                                                                                                                                                                                                                                                  |
| ------------------------ | --------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ハマったもの（タイトル） | 必須      | 20文字まで     | レーン幅を超える場合は折り返して複数行で全文表示（自動縮小はしない）。全角文字＋コメントの最悪ケースでもブロックからはみ出さないことを実描画で確認済み。アニメ・ゲームに限らず趣味全般を想定し、かつ書く粒度（ジャンル／作品／キャラ・カプ等）を限定しない名称にした（詳細は7章参照） |
| 一言コメント             | 任意      | 20〜30文字ほど | 画像は付けない方針。ブロック内にタイトルより小さい別カラーの2行目として表示。タイトル・開始年〜終了年と同じフォームでまとめて入力する（詳細は3.5・5章参照）                                                                                                                           |
| カラー                   | 任意      | ―              | 未指定時はランダムで自動割り当て。ユーザーがスウォッチから手動で変更可能（自動提案機能なし）                                                                                                                                                                                          |

### 3.5 項目の登録単位（グループ）

- 1件の項目は、タイトル・開始年〜終了年・コメント・カラーをまとめて1回の登録操作で入力する（詳細は5章・7章参照）
- 開始年〜終了年の範囲内の各年に、同じ内容（タイトル・コメント・カラー）を持つ項目として保存される。内部的には登録のたびに発行する1意のID（`groupId`）でこれらを束ねて管理しており、年表側の「連続して線がつながる」表現（4.3参照）や、編集・削除もこの単位で行う
  - かつては年ごとに個別にタイトルを入力し、複数年にまたがる継続は「タイトル文字列の完全一致」で見た目上つなげる方式だった（前年・翌年から引き継ぐ「継続入力チップ」、まとめてタイトルを変更する「前方まとめ編集」などの補助機能で運用をカバーしていた）。年ごとに順番に入力する方式は、特に継続年の扱いが取り回しづらいという指摘を受け、開始年〜終了年をまとめて指定しグループ単位で管理する今の方式に変更した（詳細は7章参照）
  - 表記が同じでも登録操作が別であれば別グループとして扱われる（例：同じタイトルで離れた年に別々に登録した場合、両者は自動ではつながらない。つなげたい場合は範囲を1つにまとめて登録し直す）

### 3.6 上限を超える登録の扱い

- 範囲（開始年〜終了年）内のどこか1年でも上限（3件）に達している場合、その登録・編集操作は**全体を行わない**（一部の年だけ反映される、といった中途半端な状態にはしない）
- エラーメッセージで、上限に達している年を案内する

## 4. 年表デザイン仕様

### 4.1 全体レイアウト

- 縦並びリスト型（上から下に時間が流れる）
- 生成画像は1枚に収める。ページ分割はせず、内容量に応じて縦方向に伸びていく可変長画像
- 高さ可変。横幅は、表示範囲内で実際に使われているレーン数（1〜3）に応じて自動で変わる
  - レーンが1列しかない場合に右側へ余分な余白ができるのを防ぐため
  - ただし見出し（タイトル）が窮屈にならないよう、最小幅は下限として維持する

### 4.2 年軸

- 左端に年の目盛り（小さいドット＋年数字）を配置
- 年数字は4桁フルで表示する（例：2024）。当初は下2桁の略記（'24）だったが、わかりやすさ・見た目の存在感を優先してフル表記に変更した
- 目盛りのドットは各年の**上端**に配置し、ジャンルブロックは「年と年の間」の空間に収まるように配置する

### 4.3 ジャンルブロック

- 白背景の上に、パステルカラーのブロック（角丸・薄い枠線・柔らかいドロップシャドウ）として表示
- レーン（列）は最大3列まで（年間の項目数上限と連動）。カード全体の横幅は実使用レーン数に連動する（詳細は4.1参照）
- 複数年にまたがって連続する項目は、線でつながって見えるように同色のブロックが縦に連続する
- ブロック内テキストは左上詰め
  - 1行目：ジャンル名（太字）
  - 2行目（コメントがある場合のみ）：一言コメント（小さめ・薄い色）
- 吹き出し風（しっぽ付き）の装飾は使わない
- ブロックはタップ／クリック可能。押すとその項目の登録フォームを編集モードで開く（詳細は5章・7章参照）。プレビューを見て気づいた修正のために毎回入力フォーム側で該当欄を探す手間を減らすための導線であり、書き出し対象（`exportTargetRef`）内の見た目自体は変えない（`cursor: pointer`やホバー時の明度変化はインタラクション時のみのCSSのため、書き出し画像には影響しない）

### 4.4 配色・雰囲気

- 背景は白
- ブロックの配色はパステル系（濃い原色は避ける）、全体的に柔らかい印象
- アクセントとして、線画のきらめき・リング・波線などのSVG装飾を控えめに散らす（メンフィス風の図形も参考にしつつ、やや洗練させたもの）

### 4.5 見出し・フッター

- 見出しは「（表示名）のオタク年表」の1行表示、傾き等の加工はしない
  - 表示名はプレビュー画面の書き出し対象の外にある入力欄（「見出しの名前」、最大10文字）で自由に設定できる。未入力時は「わたし」がデフォルトで、これまで通り「わたしのオタク年表」になる
  - 表示名はlocalStorageに年表データとは別キーで保存し、次回訪問時も引き継がれる
- 年の範囲バッジは表示しない（年軸に各年の年数字がフル表示されるため冗長と判断し廃止）
- 大きなブランドロゴ等は入れない（フッターに「#オタク年表メーカー で作成」と小さく署名程度）

### 4.6 シェア機能

- 「完成！」ボタンを押すと画像を生成し、生成した画像をその場に大きく表示する画面（画面全体を覆う専用ビュー。`CompleteFlow`）へ切り替わる。かつてはPC・モバイルで保存・シェアの方式を完全に分けていたが（PCはダウンロードボタン＋Web Share APIフォールバック）、他社の類似メーカー（コアラのマーチくんメーカー）を参考に、PC・モバイルの分岐自体を廃止しこのフローに一本化した（詳細は7章参照）
  - 画像の下に、太字で保存方法の案内（スマホなら「▲画像を長押しして保存▲」、PCなら「▲画像を右クリックで保存▲」。`isMobileDevice()`で出し分ける）、その下に「完成した年表をXでシェアしよう！（保存した画像を添付してポストしてね）」という案内文、さらにその下にXの公式ロゴアイコン＋「ポストする」というボタン（`XLogoIcon`）を配置する。「編集に戻る」ボタンで、画像生成前の編集可能なプレビューにいつでも戻れる
  - PCも含めて、保存はOS標準の操作（右クリック→「名前を付けて画像を保存」等／モバイルは長押し）に委ねる方式に一本化したため、`<a download>`によるファイルダウンロードや、PC向けに用意していたWeb Share APIフォールバックの経路は廃止した。OS標準の手動保存操作はJSの高度なAPIに依存しないため、Web Share API・ファイルダウンロードのどちらも機能しないことがあるX・LINEのアプリ内蔵ブラウザ（WebView）を含め、環境を問わず一律でこの方式が使える
  - 「ポストする」ボタンを押すと、投稿画面へ即座には遷移せず、いったん「画像の保存はしましたか？」という確認オーバーレイを挟む（保存し忘れたままシェアしてしまう事故を防ぐためのワンクッション。詳細は7章参照）。オーバーレイには「①画像を保存しよう」「② 「Xポストする」ボタンを押してシェア」の案内と、「戻る」「ポストする」の2ボタンを配置し、実際にXの投稿画面（intent URL）を開くのはオーバーレイ内の「ポストする」の方
  - オーバーレイ内の「ポストする」は`window.open()`ではなく実体が`<a href>`の通常のリンクにしている。`window.open()`を非同期に呼ぶとポップアップブロックの対象になりうることが判明したため（詳細は7章参照）、通常のリンクタップというブラウザの基本機能に寄せることで、アプリ内蔵ブラウザを含めどこでも確実に開けるようにした
  - かつてはモバイルでもOSの共有シート（`navigator.share()`）が使える環境ではそれを優先し、対応環境では画像・キャプション・URLを自動でまとめて渡していた。しかしX（Twitter）のアプリ内蔵ブラウザはUser-Agentに一切目印を残さない既知の問題があり、「環境を判定して分岐する」実装では検出できない環境が必ず残ってしまうことが分かった。判定ロジックの複雑さや、判定漏れによる不具合の再発（詳細は7章参照）を踏まえ、環境判定に依存しない方式へ統一した（最初はモバイルのみ、後にPCも含めて完全統一。詳細は7章参照）
- X・LINEのアプリ内蔵ブラウザ自体への対策として、LINEはUser-Agentに`Line/`という目印が付くため検出可能。`index.html`に、Reactが起動するより前・できるだけ早いタイミングで動くインラインスクリプトを追加し、LINEの内蔵ブラウザで開かれたことを検出したら、URLに`openExternalBrowser=1`を付けて開き直すことで標準ブラウザ（Safari/Chrome）へ自動的にハンドオフする（LINEが公式に提供している仕組み）。標準ブラウザへ切り替わった後は同じUser-Agentにならないため無限リダイレクトにはならない。データはlocalStorageに保存されておりドメイン単位で共有されるため、リダイレクト後も引き継がれる
  - 保存・シェアが上記の通り環境非依存の方式になったため、この自動脱出への依存度は下がったが、保険として残している
  - X（Twitter）のアプリ内蔵ブラウザは同じ方式で検出できないが、保存・シェア自体が環境を問わず動く方式になったため、追加の対策は不要と判断した
- シェア時（intent URLの`text`）には、次の投稿文を自動で組み立てて渡す（`buildTwitterIntentCaption`。詳細は7章参照）
  ```
  （表示名）のオタク年表📚✨
  🌟作成した画像を添付してね🌟

  ---

  あなたは今まで、何にハマってきた？
  好きだった作品、推し、ジャンル……
  ぜんぶ並べて、あなただけのオタク年表を作ろう！
  #オタク年表メーカー
  ```
  - 1行目の表示名は見出し（4.5参照）と同じ値を使い、呼び方が食い違わないようにしている（`buildShareCaption`）
  - 2行目は、画像が自動添付されず投稿画面に切り替わるとアプリ側の保存案内が見えなくなるため、投稿欄のテキスト自体に添付を促す一言として常に含めている
  - 3行目以降は、投稿を見た人がアプリへ辿ってきてくれるようにするための紹介文（拡散導線）
  - ハッシュタグはサービス名で検索しやすいよう「#オタク年表メーカー」単体で完結させ、後ろに文言を続けない（「#オタク年表メーカーで作成」のように地の文と繋げると別のタグになってしまうため）
  - サービスの公開URLはintent URLの`url`パラメータとして`text`とは別に渡しており、投稿文自体にはURLを含めていない（Xが投稿文の末尾に自動で付け足す）
  - 添付画像があるとXのリンクカードが表示されないのはXの仕様上の正常な挙動と割り切り、「リンクカードを出す」ことは目的にしていない（URLはキャプション同様にただ渡すのみ）
- サービス公開ページ（`index.html`）にOGP／Twitter Card用のメタタグと専用のシェア画像（`public/ogp.png`）を用意し、URLをシェアした際にリンクカードとして表示されるようにしている（画像を添付しない共有・URLのみの共有では引き続き有効）
- 画像書き出し（PNG化）で使うWebフォントの埋め込みCSSは、プレビュー表示時に先読み・キャッシュしておき、「完成！」ボタンをクリックした時点では再取得しないようにしている（詳細は7章参照。Google FontsのCJKサブセット分割の都合で、キャッシュなしだと1クリックごとに数百件規模のフォントファイル取得が発生し、体感速度に大きく影響していたため）。PC・モバイルの分岐を廃止したことで、この先読みも両者で同じコンポーネント（`CompleteFlow`）から一律に行われるようになった
  - WebKitエンジンで動くブラウザ（iOS上の全ブラウザ、およびデスクトップ版Safari。`needsFontEmbedWorkaround()`で判定）に限り、`exportNodeAsPngBlob`が書き出しのたびに必ず2回連続で内部のラスタライズ処理を行い、1回目（ダミー、結果は破棄）の直後に2回目（実際に使う結果）を返す。これらのブラウザではそのページで最初の書き出し呼び出しだけ埋め込みフォントがラスタライズ結果に反映されず標準フォントで焼き込まれる既知の挙動があり、これを毎回のダミー書き出しで確実に消費しておくための対策（詳細は7章参照）。フォント埋め込みCSS自体は先読み・キャッシュ済みのため2回呼んでも再取得は発生せず、増える処理はラスタライズ分のみ
  - 先読み・キャッシュしたフォント埋め込みCSSに、実際に使っている2書体（Zen Maru Gothic／Zen Kaku Gothic New）の`@font-face`ルールが両方含まれているかを確認し、不足していればキャッシュせず失敗として扱う。Google Fontsのスタイルシート読み込みが先読みのタイミングにまだ間に合っていない場合に空・不完全なCSSが返ってくることがあり、これをそのままキャッシュしてしまうとページを再読み込みするまでずっとフォールバックフォントで書き出され続けてしまうため（詳細は7章参照）
- 保存が実際に完了したかはPC・モバイルどちらも手動操作（右クリック保存・長押し保存）でありJSから検知できないため、「完成ビューが表示された（保存操作ができる状態になった）」ことを保存の代理指標として、GA4へ`image_save`イベントを送る。実際に投稿画面を開いた時点（確認オーバーレイ内の「ポストする」をクリックした時点）で`share`イベントを送る。環境を判定しない方式に統一したことに合わせ、`image_save`の`method`もPC/モバイルを区別しない`manual_save`を使う（`share`は`twitter_intent`のまま）。どちらのイベントも、その時点で年表に入っている項目数（全年合計、`item_count`）をパラメータとして付与する（詳細は7章参照）

## 5. 入力フォーム仕様

- 「項目登録」フォーム（`ItemGroupForm`）を常設し、タイトル・開始年〜終了年・コメント・カラーをまとめて1回で登録する（詳細は3.5・7章参照）
  - タイトル：必須、20文字まで
  - 開始年・終了年：それぞれプルダウンで選択（新しい年が上）。1年だけの項目は同じ年を開始・終了の両方に選ぶ。開始年が終了年より後になっている場合はエラーメッセージを出して登録しない
    - 新規登録時は、終了年を一度も直接変更していない間、終了年は開始年の選択に自動で追従する（1年だけの項目が最も多いはずのため。詳細は7章参照）。終了年を一度でも直接変更すると、それ以降は開始年を変えても終了年は動かなくなる（複数年の範囲を意図的に設定したとみなす）。編集時は既存の範囲を意図的なものとして扱い、この自動追従は最初から無効になっている
  - 一言コメント：任意。2行ぶんの高さを持つtextarea＋右下に文字数カウンター（例：12/30）を表示。プレースホルダーには「例：沼落ちした」と実例を1つ添え、何を書けばいいか分からず立ち止まってしまうのを防ぐ（詳細は7章参照）
  - カラー：5色のスウォッチからタップで選択するシンプルなUI（複雑なカラーピッカーは使わない）。フォームを開いた時点で自動でランダムな色が選ばれており、そのままでもよいし自由に変更できる。ラベルに「カラー（ジャンルなどで自由に色分けできます）」と一言添え、ジャンルなどで意図的に色分けする使い方ができることを伝えている（詳細は7章参照）
  - 範囲内のどこか1年でも上限（3件）に達している場合は、登録・更新を行わずエラーメッセージのみ表示する（3.6参照。部分的な登録はしない）
  - 新規登録に成功すると、フォームは空の新規登録状態に戻り「『（タイトル）』を登録しました」という確認メッセージを一時的に表示する。連続してテンポよく次の項目を登録できる
  - 開始年・終了年のプルダウンの直下に「＋もっと過去の年を追加する」を配置する。この操作の目的（選べる年の選択肢を増やすこと）に最も近い場所へ置いている（詳細は7章参照。かつては下記の項目一覧の一番下に常設していたが、一覧が伸びるほど手が届きにくくなるという指摘を受けて移した）
  - PC幅（lg:）では、このフォーム自体もsticky指定で画面上部に留まる（詳細は2章・下記・7章参照）
- フォームの下に、登録済みの項目一覧（`ItemGroupList`）を表示する
  - 開始年の若い順に並べる
  - **入力した項目だけを表示し、未入力の年やスロットはそもそも表示しない**（かつては年ごとにカードを常設し、未入力の年も空欄のまま表示していたが、登録した内容だけを一覧できる方が見通しがよいという判断から変更した。詳細は7章参照）
  - 各行に「（年の範囲）（タイトル）（コメント。PC幅のみ表示）」とカラーのドットを表示する
  - 行をクリックすると、上のフォームが編集モードに切り替わり、その項目のタイトル・開始年〜終了年・コメント・カラーが入った状態で開く（詳細は3.5参照）。「更新する」で保存するとフォームは新規登録状態に戻り、「キャンセル」で編集を中断できる。「この項目を削除」から確認ダイアログ（ヘッダーの「全部消す」と同じ自前のモーダルを再利用）を経て削除できる
- プレビュー上のブロックをタップすると、入力タブへ自動で切り替わり（PCでは常に両パネルが見えているため見た目に影響しない）、その項目の登録フォームが編集モードで開き、タイトル欄までスムーズスクロール＋フォーカスする（詳細は4.3・7章参照）。フォームはページ内に常に1つだけのため、対象を絞る目印（`data-item-form-title`）はIDに依存しない（かつての、項目ごとに存在した年カードの中から該当欄を`data-comment-for`属性で探し当てる方式より単純になった）
- PC幅（lg:）では、入力フォーム・プレビューの両パネルともスクロールに追従するsticky指定にしている（詳細は2章・7章参照）。登録済み項目一覧が伸びて入力パネル全体の高さが画面の縦幅を超えても、登録フォーム自体は常に画面内に留まり、一覧側だけがパネル内でスクロールする
- ヘッダーに「全部消す」ボタンを設置し、入力済みの年表データ（localStorage）を一括削除して初期状態に戻せる。確認ダイアログ（アプリのデザインに合わせた自前のモーダル。ブラウザ標準のconfirm()はURLが表示されてしまうため使わない）を挟み、誤操作による喪失を防ぐ
- ヘッダーのタグライン「ハマってきたものを年表画像に」は、PC以降ではタイトルと同じ行にインライン表示、スマホでは2行目のサブタイトルとして常時表示する（詳細は7章参照）
- ページ最下部にフッターを設置し、お問い合わせ用のGoogleフォームへのリンクと、プライバシーポリシーへのリンクを案内する（`Footer`コンポーネント。年表画像内のフッター署名とは別物）
  - プライバシーポリシーは`public/privacy.html`という、Reactアプリの外側にある素の静的HTMLとして用意している（このアプリはルーティングを持たないSPAで、1ページ増やすためだけにルーターを導入するほどでもないため）。Google Analytics（GA4）がCookieを利用してアクセス解析を行っている旨などを記載する
- 初回訪問時のみ、スポットライト式のチュートリアルオーバーレイを2ステップ表示する（`TutorialOverlay`コンポーネント。詳細は7章参照）
  - ステップ1：入力タブの入力エリア全体にスポットライトを当て、「ここから年表を作ろう」と案内
  - ステップ2：プレビューエリア全体にスポットライトを当て、「入力するとリアルタイムで反映」と案内（スマホでは「次へ」を押すと自動でプレビュータブに切り替わる）
  - ✕ボタンでいつでも終了でき、終了（✕、または最終ステップの完了）するとlocalStorageに記録され、次回以降は表示しない
- プレビューエリアがまだ何も入力されていない空の状態のときだけ、「こんな年表が作れるよ（サンプル）」という一言とともに完成イメージのサンプル画像を表示する（詳細は7章参照）
  - 既にOGP用に用意済みの`public/ogp.png`をそのまま流用しており、新規のアセット追加はしていない
  - 表示は書き出し対象（`exportTargetRef`）の外に置く。中に置くと、ユーザーが何も入力していない状態で「画像として保存」を押した場合に、サンプル画像ごと書き出されてしまうため（見出しの名前入力欄を外に置いているのと同じ理由）
  - 年ごとの項目を1件でも入力した時点で自動的に消える。ヘッダー画像等の常時表示物と異なり、役目を終えたら画面を占有し続けない

## 7. 検討の経緯（デザイン変遷メモ）

デザインは複数回のイテレーションを経て現在の形に落ち着いた。

1. 年バッジ＋作品チップ形式 → 年が目立ちすぎるとの指摘
2. サブウェイマップ風（ジャンルが線として主役）→ 方向性採用
3. 正方形固定＋ページ分割 → 「1枚の縦長画像」に変更
4. ミント背景＋シールデコ風 → 「白背景がよい」と方向転換
5. メンフィス風図形＋吹き出しバッジ → 吹き出しは不要、装飾はもう少し洗練させる方向に
6. コメントを専用列に配置 → ビジーで紐付けが分かりにくいとの指摘
7. コメントをハイブリッド配置（隣接／専用列の使い分け）→ それでも紐付けが分かりにくい
8. **最終形：コメントをブロック内部に内包**（タイトル＋小さい2行目）→ 採用
9. 配色をビビッド→パステルに変更、ブロックサイズ・行間を拡大、テキストを左上詰めに調整
10. 継続項目の引き継ぎチップを前年参照→翌年参照に変更。入力フォームは新しい年が上に並ぶため、上から順に埋めていくと前年参照では常に未入力のデータを見に行くことになり噛み合わなかった。翌年（すぐ上のカード）参照にすることで解消し、「＋もっと過去の年を追加する」で末尾に追加していく体験も変えずに済んだ
11. 継続入力チップを翌年参照のみ→前年・翌年の双方向に変更。上から新しい年順・下から古い年順のどちらで埋めても引き継ぎ候補が出るようにするための拡張。あわせて、同じジャンル名を持つ項目間でコメントを自動同期する機能を追加し、フィールド名も「作品名」→「ジャンル名」に変更（アニメ・ゲームに限らない趣味全般を扱うため）
12. ヘッダーに「全部消す」（全データリセット）機能を追加。動作確認・作り直しのたびにlocalStorageを手動でクリアする必要をなくすため。あわせて、シークレット／プライベートブラウジングで「画像として保存」が失敗する事例を調査。iOSのWeb Share API（`navigator.share`）はプライベートブラウジング中に`canShare`がtrueを返しつつ`share()`自体が拒否される既知の問題があるため、キャンセル以外の失敗時は通常のダウンロードに自動フォールバックするよう変更。あわせて、ダウンロード処理でBlob URLをclick()直後に同期的にrevokeしていた箇所も、ブラウザの読み込みより先にURLが無効化される競合を避けるため遅延させた
13. 「全部消す」の確認をブラウザ標準の`window.confirm()`から自前のモーダルダイアログに変更。`confirm()`は「（ホスト名）の内容」のようなユーザーに無関係な文言が必ず付き、デザインをコントロールできないため
14. 年表カードの横幅を固定600px→実使用レーン数（1〜3）に応じた可変幅に変更。レーンが1列しかないときに右側へ余分な余白が目立つとの指摘のため。レーンは1つあたり固定px幅とし、列数分だけカード全体の幅を伸縮させる。ただし見出し（タイトル＋年範囲バッジ）が窮屈にならないよう最小幅は維持する
15. 入力フォームの一言コメント欄を1行input→2行textarea＋文字数カウンター表示に変更。1行のままだと長めのコメント入力中に先頭が見えなくなる、上限文字数がわからず途中で入力できなくなって戸惑う、という指摘のため。任意項目としての圧迫感を避けるため、textareaの高さは2行までに留めた（自動拡張はしない）
16. 年表デザインを3点調整。(1)右上の年範囲バッジを廃止（年軸の年数字をフル表示にしたことで冗長になったため）(2)年軸の年数字を下2桁略記（'24）→4桁フル表示（2024）に変更し、フォントサイズ・色味も少し存在感を出す方向に調整 (3)フッター署名・Xシェアのデフォルトキャプションを、ハッシュタグ「#オタク年表メーカー」単体で完結させる形に変更（従来は「#オタク年表メーカーで作成」と地の文が繋がっており、サービス名そのもののハッシュタグとして検索しづらかったため）
17. 「Xでシェア」で投稿画面が about:blank のまま開かず、もう一度押すと開くという不具合を修正しようとした（一時的な変更）。空タブを先に開いてエクスポート完了後にURLを差し替える実装が、処理に時間がかかった場合にポップアップブロック判定に引っかかることがあると考え、`window.open()`自体をクリックハンドラの同期実行区間で確定URLを渡して直接呼ぶように変更した。しかし次の18で判明した副作用により、この変更は差し戻すことになった
18. 17の変更により、「Xでシェア」でクリップボードへの画像コピーが常に失敗するようになっていた（貼り付けても画像が出てこない）ことが判明し、17を差し戻して元の「空タブを先に開く」方式に戻した。原因：`navigator.clipboard.write()`はページがフォーカスを失うと`NotAllowedError: Document is not focused`で失敗する仕様があり、17の変更で実URL（X）へ即座に遷移するようにした結果、スマホではXのintent URLがネイティブアプリへの丸ごとの切り替えを引き起こし（ブラウザごとバックグラウンドになる）、その後のクリップボードコピーが確実に失敗するようになっていた。実URLへの遷移をクリップボードコピーの後に行う（＝17以前の順序）ことで、コピーの間はページのフォーカスが保たれるため解消した。17で心配していた「まれなポップアップブロック」よりも「クリップボードコピーが100%失敗する」方が実害が大きいと判断し、こちらを優先した
19. 18の方式に戻したところ、17で対処しようとしていた「投稿画面がabout:blankのまま開かない」不具合がやはり再発したため、根本的に方針転換した。クリップボードコピー（フォーカス維持が必須）と投稿画面を早く確実に開くこと（フォーカスを手放してよい）はそもそも両立しないと判断し、クリップボード経由の自動貼り付けを撤廃。画像は常にダウンロードし、投稿欄への添付は手動で案内する方式に一本化した。ダウンロードはフォーカス状態に依存しないため、投稿画面はユーザー操作直後に確定URLで直接開ける（17と同じ開き方だが、クリップボードを使わないため副作用が起きない）。あわせて、サービスの拡散のためXシェアのintent URLの`url`パラメータにサービス公開URLを付与するようにした
20. 19で「投稿画面を先に開く→画像をダウンロード」の順にしたところ、スマホの実機で「Xアプリへ遷移した後、画像が写真フォルダに保存されていない。ブラウザに戻るとダウンロード確認のダイアログが放置されていた」という報告があった。Xのintent URLへの遷移でブラウザごとバックグラウンドになり、その後に行うダウンロードの確認ダイアログ等をユーザーが見られないまま終わっていたと判明。ダウンロードとwindow.open()の順序を入れ替え、「画像をダウンロード→投稿画面を開く」に変更した。トレードオフとして、エクスポートに時間がかかった場合にwindow.open()自体がまれにポップアップブロックされる可能性が復活するが、その場合でも画像は既に保存済みのため、「画像が保存されないまま投稿画面だけ開く」場合より実害は小さいと判断した。あわせて、シェアされたURLがXでリンクカードとして表示されるよう、`index.html`にOGP／Twitter Cardのメタタグと専用画像（`public/ogp.png`、アプリの実際の見た目を模した1200×630のバナー）を追加した
21. 「画像として保存」「Xでシェア」のレスポンスが遅いという報告を受け、原因を調査。書き出し処理（`html-to-image`の`toBlob()`）はDOMをSVG化する際にWebフォント（Zen Maru Gothic / Zen Kaku Gothic New）をbase64で埋め込むが、この埋め込み処理は`@font-face`をフォントファミリー名だけでマッチさせ、実際に使われている文字（unicode-range）は見ていないことが判明。Google FontsはCJK対応のためこの2書体を大量のunicode-rangeサブセットファイルに分割して配信しており、実測でCSSレスポンスに729個の`@font-face`ルール（＝729個のフォントファイル）が含まれ、ボタンを押すたびに埋め込み処理がこれを丸ごと取得しようとしていた。年表で使うフォントファミリーはデータ内容に関わらず常に同じ（固定）で、事前に計算しておいて使い回すことに支障がないため、書き出し用の埋め込みCSSをプレビュー表示中に先読み・キャッシュし、ボタンクリック時は再取得せずキャッシュを再利用するよう変更した。2回目以降の書き出しはこのフォント取得コストがゼロになる（Playwrightでの検証では約9.5秒→66msに短縮）。初回の書き出しにかかるコストそのものは変わらないため、より根本的な対策（フォントを自前でサブセット化してローカルホストする等）は今後の検討課題として残す
22. 「Xでシェア」を、画像を添付するとX側の仕様でリンクカードが出ない、投稿欄への手動添付が必要、といった不満から方針転換。X限定ではなく`navigator.share()`によるOS標準の共有シート経由で画像・キャプション・URLをまとめて渡す方式に変更した（共有シートに画像ファイルを渡せる環境、主にスマホが対象）。共有シート経由なら添付が自動化され、宛先もX・LINE・Instagram・メールなど任意に選べる。これに伴いボタン名も、宛先がXとは限らないことが伝わるよう「Xでシェア」から「シェア」に変更した。ただしWeb Share APIはデスクトップブラウザでの対応にばらつきがあるため、`navigator.canShare({ files: [...] })`による機能検出で非対応と判定された環境（主にPC）では、ボタン名を「Xでシェア」のまま維持し、従来の「画像をダウンロード→Xの投稿画面を開く」方式にフォールバックする。あわせて、共有シート経由でもX上でのリンクカード表示は目的にしないことを明確化した（添付画像がある場合にカードが出ないのはX側の仕様として許容する）。ボタン下のヒント文言も、フォールバック時（PC）のみ表示するよう変更した（共有シートは説明不要なUIのため）
23. 22の方式をiOS×Chromeの実機で検証したところ、画像とキャプションはXの投稿画面に渡るものの、URLだけが本文に含まれないという不具合が報告された。調査の結果、`navigator.share()`に`files`と`url`を同時に渡すと、WebKit（iOS Safari／Chrome for iOSはいずれも内部的にWebKitを使用）では`url`が共有結果から欠落することがある既知の制約に該当すると判明（filesを渡す場合は他のフィールドの扱いが不安定になることがWebKit側で報告されている）。Androidの共有（Intent.ACTION_SEND）もそもそもtextとurlを別フィールドとして渡せず1本の文字列に結合される仕様であるため、いずれの環境でも「urlフィールドは信用せず、共有したい文字列は全てtextに含める」方が確実だと判断。`url`を独立したフィールドとして渡すのをやめ、キャプション文字列に`\n`区切りでURLを直接埋め込んで渡すように変更した
24. コメントの自動同期（3.6）と同様に、カラーも同じジャンル名を持つ項目間で同期して表示するよう変更した。それまではカラーが同期対象になっておらず、同じジャンル名でも年によって違う色になりうる状態だった。コメント同期のロジック（`commentSync.ts`）を拡張し、ファイル名も実態に合わせて`itemSync.ts`に変更。コメントとカラーで引き継ぎ方針を変えている点に注意：コメントは自由記述なので既存項目に何か入力されている場合のみ引き継ぐ（空なら上書きしない）が、カラーはジャンルの識別子的な位置づけのため、既存項目が見つかれば常にそちらの色に揃える（新規項目作成時にランダムで割り当てられた色を上書きする形になる）
25. 見出し「わたしのオタク年表」の「わたし」部分をユーザーが自由に設定できるようにした（例：「𓏸𓏸のオタク年表」）。プレビュー画面の書き出し対象（exportTargetRef）の外に「見出しの名前」という入力欄を新設し、そこに入力した表示名を見出しに反映する。書き出し対象の中に入力欄を置くと、入力欄自体が画像として書き出されてしまうため、外に配置する必要があった。表示名は年表データ（years）とは別のlocalStorageキーで保持し、次回訪問時も引き継がれる。最大文字数は6文字とした（見出しがカードの最小幅から1行ではみ出さない範囲を、実機描画で確認した上で決めた）。また、Xシェア時のデフォルトキャプション（「わたしのオタク年表 #オタク年表メーカー」）も見出しと同じ表示名を使うように変更し、見出しとシェア文言で呼び方が食い違わないようにした
26. 25で決めた表示名の最大文字数（6文字）が狭すぎるとの指摘を受け、10文字まで拡張した。文字数を増やすと見出しの横幅も伸びるため、それに合わせて年表カードの最小幅（`timelineLayout.ts`のMIN_CHART_WIDTH）も300→400に拡大した。ひらがな・カタカナ・半角英字それぞれ最大文字数いっぱいの表示名で見出しを実描画し、カードからはみ出さないことを確認した上で幅を決めている
27. 「見出しの名前」入力欄が小さすぎるとの指摘を受け、最大文字数（10文字）を入力しても入力欄内で文字が見切れないサイズまで拡幅した（w-24→w-56）。あわせて、お問い合わせ先として作成されたGoogleフォームへの案内をページ最下部のフッターに追加した（`Footer`コンポーネントを新設）。年表画像内のフッター署名（「#オタク年表メーカー で作成」）とは別物で、アプリのページ全体に対する案内として設置している

37. 36のクイック入力機能に関連して、「間違えた年に入力してしまった時、別の年に動かしたいが、今は一度削除して入力し直す必要があり手間」という指摘があった。削除→再入力だと、タイトルだけでなくコメント・カラーも失われてしまう（同名項目が他に無ければ引き継ぎ元も無いため）。ドラッグ＆ドロップでの並べ替えも検討したが、10年以上に渡る縦長のリストをスクロールしながらのドラッグ操作はモバイルでの実装・操作性のハードルが高く、このアプリの規模には過剰と判断し見送った。代わりに、各項目に「年を移動」ボタンを追加し、押すと現在の年以外を選べるプルダウンが現れ、選択すると即座にその年へ移動する方式にした（QuickAddCardの年選択と同じ発想）。実装は、移動元の年からの削除・移動先の年への追加をそれぞれ既存の`onChangeYearItems`（＝`updateYearItems`）で行うだけの単純な2段操作にした：`useState`の関数型更新はReactが呼び出し順に順次適用することを利用し、同一イベントハンドラ内で2回`onChangeYearItems`を呼んでも、2回目は1回目の更新が反映された状態から計算される。これにより、移動先の年に既に上限（3件）まで項目がある場合は移動を行わずエラー表示のみ行う、というガードも1箇所（`InputFormPanel`）に書くだけで済んだ。移動した項目のタイトル・コメント・カラーはオブジェクトごとそのまま移動先の年の配列に積むだけなので、`useTimelineData`側の新規項目引き継ぎロジックに一切手を入れずに済んでいる（同名項目が別途存在する場合は、そちらの色・コメントに揃うという既存の自動同期がそのまま働くのも意図通り）
38. 「プレビューを見て直したい箇所に気づいても、入力フォームに戻るのが面倒」という相談があった。プレビュー上で直接コメント・カラーを編集できるポップオーバーを検討したが、(a)書き出し対象（`exportTargetRef`）の外にポップオーバーを配置する実装、(b)モバイルでは縮小表示されるブロックへの正確なタップ操作、といった論点があり実装コストは中程度になると判断。まず低コストな案（プレビューのブロックをタップすると入力フォーム側の該当欄へジャンプするだけ）を試し、それでも「その場で完結させたい」という感覚が残るようなら本格的なポップオーバーに投資する、という段階的な進め方にした。実装は、クイック入力（36）の「コメント・色を編集 →」で使ったジャンプの仕組み（`data-comment-for`属性を目印にした`focus`＋`scrollIntoView`）をそのまま再利用：`TimelineChart`の各ブロックに`onItemClick`を渡すとタップ可能になり、`PreviewPanel`経由で`App`まで項目IDが渡ってくる。`App`側では、モバイルタブの切り替え（`setMobileTab('input')`）と直後にジャンプ先の項目IDをセットする状態更新を同じイベントハンドラ内で行い、`useEffect`でDOM検索を行うことで、タブ切り替え直後はまだ対象要素が`hidden`（display:none）で見つからない、という順序問題を避けている。ジャンプ先の状態は項目IDだけでなく`token`（実行のたびに変わる値）も持たせ、同じ項目を連続でタップしてもオブジェクト参照が変わって確実に`useEffect`が再実行されるようにした（stateを使い終えたらeffect内でnullに戻す、という実装も検討したが、oxlintの`set-state-in-effect`ルールに引っかかり不要な再レンダーを招くため見送った）。ブロックに追加した`cursor-pointer`やホバー時の明度変化はインタラクション時のみに適用されるCSSのため、書き出し画像（PNG）の見た目には影響しない。PCでは両パネルが常に表示されているためタブ切り替えは実質何もしないが、縦に長い入力欄一覧の中から該当項目まで自動でスクロール＋フォーカスされる点はPCでも変わらず有効に働く
39. 38の追加直後、「該当ブロックの一言コメント欄まで実際にフォーカスが当たった状態にしてほしい。近くの入力欄と見間違えることが多く、フォーカスまで当たっていればすぐ書き始められる」という指摘があった。原因は、38の実装がタブ切り替え後の`focus()`呼び出しを`useEffect`（タップのイベントハンドラから見て次のティック、非同期）で行っていたこと。モバイルブラウザ（特にiOS Safari）は、ユーザー操作の呼び出しスタックと直接つながっていない`.focus()`呼び出しに対して、`document.activeElement`は変更しても仮想キーボードは開かない・実質的にタップ操作からフォーカスが「地続き」に見えない、という制約があり、これが「フォーカスが当たっているように見えるのに近くの欄と見間違える」現象の原因と判断した。対処として、`useEffect`＋`jumpRequest`（itemId＋token）による非同期の仕組みを廃止し、`react-dom`の`flushSync`でタブ切り替えの状態更新を同期的にDOMへ反映させた直後、同じクリックハンドラ内で続けて`focus()`・`scrollIntoView()`を呼ぶ形に書き換えた。これによりタップ操作と同一の呼び出しスタック内でフォーカス処理が完結するようになった

48. 「X内やLINE内のブラウザで開くと、画像の保存やシェアがうまくいかない」という指摘があった。SNSでの拡散利用を主目的とするアプリの性質上、深刻度が高い不具合と判断し優先的に調査した。原因は、X・LINEなどのアプリ内蔵ブラウザ（WebView）では、`navigator.share()`（Web Share API）自体が利用できないことが多く、`<a download>`によるファイルダウンロードも「ダウンロードの意図」をアプリ側でネイティブに処理する必要がある仕組みのため、多くのアプリ内蔵ブラウザでは実装されておらず機能しない、という2つの既知の制約が重なっているためと判明した。`navigator.share()`が使えない結果、これらの環境では常にPC向けに用意していたフォールバック経路（画像をダウンロードしてからXの投稿画面を新規タブで開く方式）に入るが、そのフォールバック自体の土台（ダウンロード・新規タブを開く操作）がアプリ内蔵ブラウザでは機能しにくい、という構造だった。対処は以下の3点に分けた。(1) LINEはUser-Agentに`Line/`という目印を残す既知の仕様があり、かつLINE公式が「URLに`openExternalBrowser=1`を付けて開き直すと標準ブラウザへハンドオフする」という仕組みを提供しているため、`index.html`にReact起動前の最速タイミングで動くインラインスクリプトを追加し、LINEの内蔵ブラウザを検出したら即座にこの方式で標準ブラウザへ自動的に切り替えるようにした。データはlocalStorageに保存されドメイン単位で共有されるため、標準ブラウザへ切り替わってもそのまま引き継がれる。(2) X（Twitter）のアプリ内蔵ブラウザはUser-Agentに一切目印を残さない既知の問題があり（Xの開発者コミュニティでも指摘されている）、同じ方式では検出できない。自動対処ができない以上、共有シート非対応環境向けのヒント文言に「X・LINEなどアプリ内のブラウザで開いている場合、保存やシェアがうまく動かないことがあります。画面右上のメニューなどから『Safariで開く』を選んでからお試しください」という案内を常に含めることにした（検出できないため、条件分岐で出し分けるのではなく該当しうる全員に常に見せる）。(3) 副次的な調査で、`window.open()`（Xの投稿画面を開く処理）は失敗時に例外を投げずnullを返すだけであるにもかかわらず、従来のコードはこの戻り値を確認せず常に「投稿画面を開いた」という前提のメッセージを表示していたことが判明した。ポップアップブロックはアプリ内蔵ブラウザに限らず、書き出し処理に時間がかかった場合（実測では、フォント埋め込みCSSの取得に失敗し続ける環境等でユーザー操作からの経過時間が伸びるケースで再現した）にも起こりうるため、戻り値がnullの場合は「このブラウザでは投稿画面を開けませんでした」という正直な文言に出し分け、GA4の`share`イベントも実際に開けた場合のみ送るよう修正した。動作確認は、Playwrightで(1) LINEのUser-Agentでアクセスすると`openExternalBrowser=1`付きURLへ自動的にリダイレクトされること、既にこのパラメータが付いている場合は再リダイレクトされない（無限ループにならない）こと、通常のiOS SafariのUser-Agentではリダイレクトが起きないことを確認。(3)については`window.open()`の戻り値を強制的にnull／truthyにモックし、それぞれ対応するメッセージが表示されること、GA4の`share`イベントがnull時には送られずtruthy時のみ送られることを確認した。Xのアプリ内蔵ブラウザ自体（検出不能）や、LINEの`openExternalBrowser=1`によるハンドオフが実機で実際に機能するかどうかは、このサンドボックス環境の性質上検証できていない

62. 61の刷新後、「入力フォームも画面のスクロールに追従させられるか」「『＋もっと過去の年を追加する』が登録済み項目一覧の一番下にあるのは、一覧が伸びるほど手が届きにくくなり違和感がある」という2点の指摘があった。前者は、51・60でプレビュー側に導入した「PC幅（lg:）のみsticky指定にし、パネル自身の高さが画面の縦幅を超える場合はmax-height＋overflow-y-autoで頭打ちにして内部スクロールへ切り替える」という仕組みを、入力パネル（`ItemGroupForm`＋`ItemGroupList`）側にもそのまま適用することで対応した（`App.tsx`に両パネル共通の`STICKY_PANEL_CLASSNAME`を切り出して重複を避けた）。ただし単純に同じ処理を両パネルへ適用しただけでは、`ItemGroupForm`自体も一覧と一緒にスクロールで流れて行ってしまい、「フォームだけは常に見えていてほしい」という意図を満たせないことに気づいた。対処として、`ItemGroupForm`自身にも`lg:sticky lg:top-0`を指定し、外側のスクロール領域（入力パネルのsticky＋overflow-y-autoのdiv）を基準にフォーム自体もその領域内でさらにstickyにする、いわゆるネストしたsticky（sticky within a scrollable sticky container）の構成にした。これにより、登録済み項目一覧がどれだけ増えても、フォームは常に入力パネルの一番上に留まり、一覧側だけがそのスクロール領域内で流れる。検証中、入力・プレビュー両パネルを同じ高さで頭打ちにすると、ページ全体の高さも両パネルのうち高い方（≒画面の縦幅）程度に収まり、ページ自体はほとんどスクロールを必要としなくなる（各パネルの内部スクロールで完結する）ことも確認した。後者（「もっと過去の年を追加する」の位置）は、この操作の目的が「開始年・終了年プルダウンの選択肢を増やすこと」そのものである点に着目し、一覧の末尾ではなくプルダウンのすぐ下（`ItemGroupForm`内）へ移動した。フォーム自体がstickyになったことで、一覧がどれだけ伸びてもこの操作も常に手の届く位置に留まる。動作確認は、`npx tsc -b --noEmit`／`npm run lint`／`npx prettier --check .`／`npm run build`がいずれも成功することに加え、Playwrightで20件の項目を登録して入力パネルの高さが画面の縦幅を超える状態を作り、(1)入力パネルが頭打ちになり内部スクロール可能なこと、(2)フォーム自体がposition: stickyになっていること、(3)一覧側だけを内部スクロールしてもフォームの画面上の位置が変わらないこと、(4)頭打ちの結果ページ全体の高さがビューポート+α程度に収まること、(5)「もっと過去の年を追加する」がフォーム内から押せて年の選択肢が正しく増えること、(6)項目が少ない通常時は従来通り内部スクロールバーが出ないこと、を確認した。

63. 「終了年はデフォルトでは初期入力時、開始年と同じ年に自動で揃うようにできますか」という相談があった。登録の大多数は1年だけの項目のはずで、そのたびに開始年・終了年の両方を選ぶのは手間だと判断し、`ItemGroupForm`に「終了年を一度も直接変更していない間は、開始年の変更に終了年も追従する」という仕組みを追加した。単純に「開始年が変わったら常に終了年を開始年に合わせる」実装にすると、複数年の範囲を意図して終了年を先に広げていたユーザーが後から開始年を微調整しただけで、せっかく設定した終了年を巻き添えで消してしまう（範囲を壊してしまう）ため、`endYearTouched`という状態を持たせ、終了年を直接変更した時点で以後の自動追従を止める設計にした。新規登録に成功してフォームが空の状態に戻ると、この状態もリセットされ再び自動追従が有効になる。一方、既存グループの編集時は、フォームを開いた時点で既に持っている範囲を「ユーザーが意図して設定したもの」とみなし、`endYearTouched`を最初からtrueにして自動追従を無効にした（編集中に開始年を動かしても、既存の終了年を勝手に書き換えないようにするため）。動作確認は、`npx tsc -b --noEmit`／`npm run lint`／`npx prettier --check .`／`npm run build`がいずれも成功することに加え、Playwrightで、(1)フォームを開いた初期状態で開始年・終了年がともに最新年になっていること、(2)終了年を直接触っていない状態で開始年を変更すると終了年も追従すること、(3)終了年を一度直接変更した後は開始年を変えても終了年が追従しなくなること、(4)登録に成功してフォームがリセットされると再び追従が有効になること、(5)編集モードでは開始年を変更しても既存の終了年が動かないこと、を確認した。

64. 「『カラー』というラベルだけだと何のための操作かわかりづらい。ジャンルなどで自分で色分けすることもできる、というのを伝えたい」という相談があった。かつての年カード方式では、同じ名前の項目はカラーが自動で揃う仕組みがあったため、ラベルに「カラー（同じ名前の項目は自動で揃います）」という一言を添えて説明していたが、61のグループ方式への刷新でこの自動同期自体を廃止したため、その説明文もあわせて削除されたままになっていた（穴が空いていた状態）。今回、その位置に代わる一言として「カラー（ジャンルなどで自由に色分けできます）」を追加した。自動同期の仕組みが無くなった分、逆に「ユーザー自身の意図で自由に色分けできる」という、より率直な使い方の説明になっている。動作確認は、`npx tsc -b --noEmit`／`npm run lint`／`npx prettier --check .`／`npm run build`がいずれも成功することに加え、Playwrightでラベルが1行に折り返さず収まって表示されることをスクリーンショットで確認した。
