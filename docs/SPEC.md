# オタク年表メーカー 仕様書

自分がハマってきたものを年別に入力すると、1枚の年表画像を生成できるWebアプリ。生成した画像はXなどでシェアできる。

---

## 1. コンセプト

- 自分が今まで熱中してきたもの（作品・アイドル・趣味など）を年ごとに記録し、1枚の年表画像として可視化する
- 完成した画像はSNS（X）にシェアできる
- 簡単な作りで低コスト運用（サーバー不要、フロントエンドのみで完結）

---

## 2. 技術構成

| 項目             | 内容                                                                                     |
| ---------------- | ---------------------------------------------------------------------------------------- |
| フレームワーク   | React + Vite                                                                             |
| データ保存       | localStorageのみ（シンプル優先。エクスポート機能等は持たない）                           |
| デプロイ         | サーバー不要の静的ホスティングを想定（Vercel / Netlify等）                               |
| 画面構成         | 1画面完結型。入力とプレビューが同一画面上に並ぶ、リアルタイム連動更新                    |
| レスポンシブ対応 | PC：入力フォームとプレビューを左右並び<br>スマホ：「入力」「プレビュー」タブ切り替え表示 |

## 3. データ仕様

### 3.1 年の範囲

- デフォルトで直近10年分を表示
- 「＋もっと過去の年を追加する」ボタンで、過去方向にどんどん年を追加できる
- 終了年（＝現在）は固定。開始年をユーザーに最初に入力させる負担は避ける

### 3.2 空欄の年の扱い

- **先頭側（一番古い側）の空欄**：年表画像から除外する（ノイズ削減）
- **途中の空欄**：そのまま表示する（時間軸の連続性を保つため）

### 3.3 1年あたりの項目数

- 最大3項目まで
- **継続項目も同じ3枠の中でカウントする**（別枠ではない）
  - 例：前年から2項目を引き継ぐと、新規入力できる欄は自動的に残り1つだけになる
  - 上限に達している場合は継続入力チップ自体が表示されない（エラー案内は出さず、UI側で自然に制限する）

### 3.4 各項目のデータ

| フィールド             | 必須/任意 | 文字数上限     | 備考                                                                                                                                                          |
| ---------------------- | --------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ジャンル名（タイトル） | 必須      | 15文字まで     | レーン幅に収まらない場合はフォントサイズを自動縮小して全文表示。アニメ・ゲームに限らず趣味全般を想定するため「作品名」ではなくこの名称にした（詳細は7章参照） |
| 一言コメント           | 任意      | 20〜30文字ほど | 画像は付けない方針。ブロック内にタイトルより小さい別カラーの2行目として表示。**同じジャンル名を持つ項目間ではコメントを自動同期する**（後述）                 |
| カラー                 | 任意      | ―              | 未指定時はランダムで自動割り当て。ユーザーがスウォッチから手動で変更可能（自動提案機能なし）                                                                  |

### 3.5 継続項目の入力サポート

- 継続入力チップは**双方向**に出す。前年（1つ下のカード）・翌年（1つ上のカード）のどちらに既存項目があっても、まだ未入力の年のドラフト枠にチップとして表示される
  - 前年からの継続は「昨年から：〇〇」、翌年からの継続は「翌年から：〇〇」とラベルで区別する
  - 上から新しい年順に埋める人・下から古い年順に埋める人のどちらの入力順にも対応するための変更（経緯は7章参照。当初は翌年参照のみの片方向だった）
- チップをタップすると同じ文字列・同じカラーがそのまま入力される（表記ゆれ防止）
- 年表側の「連続して線がつながる」表現は、**ジャンル名の完全一致**で判定する。この判定はチップの参照方向とは独立しており、どちらの年から先に入力してもタイトルが一致すれば連続ブロックになる
  - 例：「日プ」→「日プ2」→「日プ女子」のように表記が変わると、たとえ同じテーマでも別ブロックとして扱われる（同じ色を手動で選べば視覚的に揃えることは可能）

### 3.6 コメントの自動同期

- 同じジャンル名を持つ項目は、年をまたいでいても「同じ対象」とみなし、コメントを自動で同期する
  - どこか1つの年でコメントを入力・編集すると、同じジャンル名を持つ他の年の項目のコメントにも即座に反映される
  - 継続入力チップから新規項目を作成した場合、既存の同名項目にコメントがあればそれを初期値として引き継ぐ
  - 新規に手入力したジャンル名がすでに他の年で使われているものと完全一致した場合も、同様にコメントを引き継ぐ
- 同期はジャンル名の完全一致で行うため、表記が変わると別項目として扱われ、コメントは引き継がれない（3.5と同じ判定基準）

## 4. 年表デザイン仕様

### 4.1 全体レイアウト

- 縦並びリスト型（上から下に時間が流れる）
- 生成画像は1枚に収める。ページ分割はせず、内容量に応じて縦方向に伸びていく可変長画像
- 高さ可変。横幅は、表示範囲内で実際に使われているレーン数（1〜3）に応じて自動で変わる
  - レーンが1列しかない場合に右側へ余分な余白ができるのを防ぐため
  - ただし見出し（タイトル＋年範囲バッジ）が窮屈にならないよう、最小幅は下限として維持する

### 4.2 年軸

- 左端に年の目盛り（小さいドット＋年数字）を配置。年は主役ではなく脇役の表示
- 目盛りのドットは各年の**上端**に配置し、ジャンルブロックは「年と年の間」の空間に収まるように配置する

### 4.3 ジャンルブロック

- 白背景の上に、パステルカラーのブロック（角丸・薄い枠線・柔らかいドロップシャドウ）として表示
- レーン（列）は最大3列まで（年間の項目数上限と連動）。カード全体の横幅は実使用レーン数に連動する（詳細は4.1参照）
- 複数年にまたがって連続する項目は、線でつながって見えるように同色のブロックが縦に連続する
- ブロック内テキストは左上詰め
  - 1行目：ジャンル名（太字）
  - 2行目（コメントがある場合のみ）：一言コメント（小さめ・薄い色）
- 吹き出し風（しっぽ付き）の装飾は使わない

### 4.4 配色・雰囲気

- 背景は白
- ブロックの配色はパステル系（濃い原色は避ける）、全体的に柔らかい印象
- アクセントとして、線画のきらめき・リング・波線などのSVG装飾を控えめに散らす（メンフィス風の図形も参考にしつつ、やや洗練させたもの）

### 4.5 見出し・フッター

- 見出し「わたしのオタク年表」は1行表示、傾き等の加工はしない
- 年の範囲（例：2019-2026）をピル型バッジで表示
- 大きなブランドロゴ等は入れない（フッターに小さく署名程度）

### 4.6 シェア機能

- 「画像として保存」「Xでシェア」ボタンを設置
- Xシェア時は「#オタク年表メーカーで作成」のようなデフォルトキャプションを自動付与
- 「画像として保存」はiOSでは共有シート経由（Web Share API）を優先するが、シークレット／プライベートブラウジング中などでWeb Share自体が失敗するケースがあるため、その場合は通常のダウンロードに自動フォールバックする（ユーザーがキャンセルした場合を除く）

## 5. 入力フォーム仕様

- 年ごとにカード状のブロックで表示（年表のブロックと統一されたデザインテイスト）
- 各年カードの構成：
  - 年ラベル（黒背景の丸ピル等）
  - 入力済みの項目（ジャンル名＋カラースウォッチ＋削除ボタン）
  - 未入力の欄は常に1つだけ表示され、入力すると自動で次の欄が現れる（上限3、継続チップ込み）
  - 前年・翌年から続いている項目がある場合の「引き継ぎチップ」表示（双方向、詳細は3.5参照）
- カラー選択：5〜6色程度のスウォッチをタップで選択するシンプルなUI（複雑なカラーピッカーは使わない）
- 一言コメント欄は2行ぶんの高さを持つtextarea＋右下に文字数カウンター（例：12/30）を表示。1行のinputだと入力中に先頭が見えなくなる・上限がわかりにくいという課題があったため
- ヘッダーに「全部消す」ボタンを設置し、入力済みの年表データ（localStorage）を一括削除して初期状態に戻せる。確認ダイアログ（アプリのデザインに合わせた自前のモーダル。ブラウザ標準のconfirm()はURLが表示されてしまうため使わない）を挟み、誤操作による喪失を防ぐ

## 6. 見送った機能（将来の拡張候補）

以下は今回のMVPでは実装せず、必要になれば後日検討する。

- **年表画面上での直接編集UI**（ドラッグでブロックの期間を伸ばす／移動する／削除する）
  - MVPではシンプルなフォーム入力方式を採用
- **画像添付機能**（作品ごとに画像を付ける）
  - ビジーになりやすいため不採用。コメントのみ採用
- **色の自動提案機能**（似た項目名から過去に使った色を提案する）
  - シンプルさ優先で不採用。色は基本ランダム割り当て＋手動変更のみ
- **データのエクスポート／インポート機能、URL共有**
  - MVPではlocalStorageのみ

## 7. 検討の経緯（デザイン変遷メモ）

デザインは複数回のイテレーションを経て現在の形に落ち着いた。

1. 年バッジ＋作品チップ形式 → 年が目立ちすぎるとの指摘
2. サブウェイマップ風（ジャンルが線として主役）→ 方向性採用
3. 正方形固定＋ページ分割 → 「1枚の縦長画像」に変更
4. ミント背景＋シールデコ風 → 「白背景がよい」と方向転換
5. メンフィス風図形＋吹き出しバッジ → 吹き出しは不要、装飾はもう少し洗練させる方向に
6. コメントを専用列に配置 → ビジーで紐付けが分かりにくいとの指摘
7. コメントをハイブリッド配置（隣接／専用列の使い分け）→ それでも紐付けが分かりにくい
8. **最終形：コメントをブロック内部に内包**（タイトル＋小さい2行目）→ 採用
9. 配色をビビッド→パステルに変更、ブロックサイズ・行間を拡大、テキストを左上詰めに調整
10. 継続項目の引き継ぎチップを前年参照→翌年参照に変更。入力フォームは新しい年が上に並ぶため、上から順に埋めていくと前年参照では常に未入力のデータを見に行くことになり噛み合わなかった。翌年（すぐ上のカード）参照にすることで解消し、「＋もっと過去の年を追加する」で末尾に追加していく体験も変えずに済んだ
11. 継続入力チップを翌年参照のみ→前年・翌年の双方向に変更。上から新しい年順・下から古い年順のどちらで埋めても引き継ぎ候補が出るようにするための拡張。あわせて、同じジャンル名を持つ項目間でコメントを自動同期する機能を追加し、フィールド名も「作品名」→「ジャンル名」に変更（アニメ・ゲームに限らない趣味全般を扱うため）
12. ヘッダーに「全部消す」（全データリセット）機能を追加。動作確認・作り直しのたびにlocalStorageを手動でクリアする必要をなくすため。あわせて、シークレット／プライベートブラウジングで「画像として保存」が失敗する事例を調査。iOSのWeb Share API（`navigator.share`）はプライベートブラウジング中に`canShare`がtrueを返しつつ`share()`自体が拒否される既知の問題があるため、キャンセル以外の失敗時は通常のダウンロードに自動フォールバックするよう変更。あわせて、ダウンロード処理でBlob URLをclick()直後に同期的にrevokeしていた箇所も、ブラウザの読み込みより先にURLが無効化される競合を避けるため遅延させた
13. 「全部消す」の確認をブラウザ標準の`window.confirm()`から自前のモーダルダイアログに変更。`confirm()`は「（ホスト名）の内容」のようなユーザーに無関係な文言が必ず付き、デザインをコントロールできないため
14. 年表カードの横幅を固定600px→実使用レーン数（1〜3）に応じた可変幅に変更。レーンが1列しかないときに右側へ余分な余白が目立つとの指摘のため。レーンは1つあたり固定px幅とし、列数分だけカード全体の幅を伸縮させる。ただし見出し（タイトル＋年範囲バッジ）が窮屈にならないよう最小幅は維持する
15. 入力フォームの一言コメント欄を1行input→2行textarea＋文字数カウンター表示に変更。1行のままだと長めのコメント入力中に先頭が見えなくなる、上限文字数がわからず途中で入力できなくなって戸惑う、という指摘のため。任意項目としての圧迫感を避けるため、textareaの高さは2行までに留めた（自動拡張はしない）
