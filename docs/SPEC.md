# オタク年表メーカー 仕様書

自分がハマってきたものを年別に入力すると、1枚の年表画像を生成できるWebアプリ。生成した画像はXなどでシェアできる。

---

## 1. コンセプト

- 自分が今まで熱中してきたもの（作品・アイドル・趣味など）を年ごとに記録し、1枚の年表画像として可視化する
- 完成した画像はSNS（X）にシェアできる
- 簡単な作りで低コスト運用（サーバー不要、フロントエンドのみで完結）

---

## 2. 技術構成

| 項目             | 内容                                                                                     |
| ---------------- | ---------------------------------------------------------------------------------------- |
| フレームワーク   | React + Vite                                                                             |
| データ保存       | localStorageのみ（シンプル優先。エクスポート機能等は持たない）                           |
| デプロイ         | サーバー不要の静的ホスティングを想定（Vercel / Netlify等）                               |
| 画面構成         | 1画面完結型。入力とプレビューが同一画面上に並ぶ、リアルタイム連動更新                    |
| レスポンシブ対応 | PC：入力フォームとプレビューを左右並び<br>スマホ：「入力」「プレビュー」タブ切り替え表示 |

## 3. データ仕様

### 3.1 年の範囲

- デフォルトで直近10年分を表示
- 「＋もっと過去の年を追加する」ボタンで、過去方向にどんどん年を追加できる
- 終了年（＝現在）は固定。開始年をユーザーに最初に入力させる負担は避ける

### 3.2 空欄の年の扱い

- **先頭側（一番古い側）の空欄**：年表画像から除外する（ノイズ削減）
- **途中の空欄**：そのまま表示する（時間軸の連続性を保つため）

### 3.3 1年あたりの項目数

- 最大3項目まで
- **継続項目も同じ3枠の中でカウントする**（別枠ではない）
  - 例：前年から2項目を引き継ぐと、新規入力できる欄は自動的に残り1つだけになる
  - 上限に達している場合は継続入力チップ自体が表示されない（エラー案内は出さず、UI側で自然に制限する）

### 3.4 各項目のデータ

| フィールド             | 必須/任意 | 文字数上限     | 備考                                                                                                                                                          |
| ---------------------- | --------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ジャンル名（タイトル） | 必須      | 15文字まで     | レーン幅に収まらない場合はフォントサイズを自動縮小して全文表示。アニメ・ゲームに限らず趣味全般を想定するため「作品名」ではなくこの名称にした（詳細は7章参照） |
| 一言コメント           | 任意      | 20〜30文字ほど | 画像は付けない方針。ブロック内にタイトルより小さい別カラーの2行目として表示。**同じジャンル名を持つ項目間ではコメントを自動同期する**（後述）                 |
| カラー                 | 任意      | ―              | 未指定時はランダムで自動割り当て。ユーザーがスウォッチから手動で変更可能（自動提案機能なし）                                                                  |

### 3.5 継続項目の入力サポート

- 継続入力チップは**双方向**に出す。前年（1つ下のカード）・翌年（1つ上のカード）のどちらに既存項目があっても、まだ未入力の年のドラフト枠にチップとして表示される
  - 前年からの継続は「昨年から：〇〇」、翌年からの継続は「翌年から：〇〇」とラベルで区別する
  - 上から新しい年順に埋める人・下から古い年順に埋める人のどちらの入力順にも対応するための変更（経緯は7章参照。当初は翌年参照のみの片方向だった）
- チップをタップすると同じ文字列・同じカラーがそのまま入力される（表記ゆれ防止）
- 年表側の「連続して線がつながる」表現は、**ジャンル名の完全一致**で判定する。この判定はチップの参照方向とは独立しており、どちらの年から先に入力してもタイトルが一致すれば連続ブロックになる
  - 例：「日プ」→「日プ2」→「日プ女子」のように表記が変わると、たとえ同じテーマでも別ブロックとして扱われる（同じ色を手動で選べば視覚的に揃えることは可能）

### 3.6 コメント・カラーの自動同期

- 同じジャンル名を持つ項目は、年をまたいでいても「同じ対象」とみなし、コメント・カラーの両方を自動で同期する
  - どこか1つの年でコメント・カラーを入力・編集すると、同じジャンル名を持つ他の年の項目にも即座に反映される
  - 継続入力チップから新規項目を作成した場合、既存の同名項目のコメント・カラーをそのまま引き継ぐ
  - 新規に手入力したジャンル名がすでに他の年で使われているものと完全一致した場合も、同様に引き継ぐ
- コメントとカラーで引き継ぎの扱いが少し異なる：コメントは自由記述のため既存項目にコメントがある場合のみ引き継ぐ（空なら上書きしない）が、カラーはジャンルの見た目上の識別子という位置づけのため、既存項目が見つかれば常にそちらの色に揃える（新規項目にはこの時点でランダムな色が割り当てられているだけなので、既存ジャンルの色で上書きする）
- 同期はジャンル名の完全一致で行うため、表記が変わると別項目として扱われ、コメント・カラーは引き継がれない（3.5と同じ判定基準）

## 4. 年表デザイン仕様

### 4.1 全体レイアウト

- 縦並びリスト型（上から下に時間が流れる）
- 生成画像は1枚に収める。ページ分割はせず、内容量に応じて縦方向に伸びていく可変長画像
- 高さ可変。横幅は、表示範囲内で実際に使われているレーン数（1〜3）に応じて自動で変わる
  - レーンが1列しかない場合に右側へ余分な余白ができるのを防ぐため
  - ただし見出し（タイトル）が窮屈にならないよう、最小幅は下限として維持する

### 4.2 年軸

- 左端に年の目盛り（小さいドット＋年数字）を配置
- 年数字は4桁フルで表示する（例：2024）。当初は下2桁の略記（'24）だったが、わかりやすさ・見た目の存在感を優先してフル表記に変更した
- 目盛りのドットは各年の**上端**に配置し、ジャンルブロックは「年と年の間」の空間に収まるように配置する

### 4.3 ジャンルブロック

- 白背景の上に、パステルカラーのブロック（角丸・薄い枠線・柔らかいドロップシャドウ）として表示
- レーン（列）は最大3列まで（年間の項目数上限と連動）。カード全体の横幅は実使用レーン数に連動する（詳細は4.1参照）
- 複数年にまたがって連続する項目は、線でつながって見えるように同色のブロックが縦に連続する
- ブロック内テキストは左上詰め
  - 1行目：ジャンル名（太字）
  - 2行目（コメントがある場合のみ）：一言コメント（小さめ・薄い色）
- 吹き出し風（しっぽ付き）の装飾は使わない

### 4.4 配色・雰囲気

- 背景は白
- ブロックの配色はパステル系（濃い原色は避ける）、全体的に柔らかい印象
- アクセントとして、線画のきらめき・リング・波線などのSVG装飾を控えめに散らす（メンフィス風の図形も参考にしつつ、やや洗練させたもの）

### 4.5 見出し・フッター

- 見出しは「（表示名）のオタク年表」の1行表示、傾き等の加工はしない
  - 表示名はプレビュー画面の書き出し対象の外にある入力欄（「見出しの名前」、最大10文字）で自由に設定できる。未入力時は「わたし」がデフォルトで、これまで通り「わたしのオタク年表」になる
  - 表示名はlocalStorageに年表データとは別キーで保存し、次回訪問時も引き継がれる
- 年の範囲バッジは表示しない（年軸に各年の年数字がフル表示されるため冗長と判断し廃止）
- 大きなブランドロゴ等は入れない（フッターに「#オタク年表メーカー で作成」と小さく署名程度）

### 4.6 シェア機能

- 「画像として保存」「シェア」（非対応環境では「Xでシェア」）ボタンを設置
- シェア時は「（表示名）のオタク年表 #オタク年表メーカー」をデフォルトキャプションとして自動付与し、サービスの公開URLも一緒に渡す（投稿から辿ってアプリに来てもらうための拡散導線）。表示名は見出し（4.5参照）と同じ値を使い、呼び方が食い違わないようにしている
  - ハッシュタグはサービス名で検索しやすいよう「#オタク年表メーカー」単体で完結させ、後ろに文言を続けない（「#オタク年表メーカーで作成」のように地の文と繋げると別のタグになってしまうため）
- 「画像として保存」はiOSでは共有シート経由（Web Share API）を優先するが、シークレット／プライベートブラウジング中などでWeb Share自体が失敗するケースがあるため、その場合は通常のダウンロードに自動フォールバックする（ユーザーがキャンセルした場合を除く）
- 「シェア」は、OSの共有シートに画像ファイルを渡せる環境（主にスマホ）では`navigator.share()`でOS標準の共有シートを開き、画像・キャプション・URLをまとめて渡す。宛先はX限定ではなくユーザーが共有シートから選ぶため、ボタン名も「Xでシェア」から汎用的な「シェア」に変更した（詳細は7章参照）
  - URLは`url`フィールドとして独立させず、キャプション文字列（`text`）に直接埋め込んで渡す。`files`と`url`を同時に渡すと、iOS（WebKit）+ Xの組み合わせで実機検証した際にURLだけが共有結果から欠落することを確認したため（詳細は7章参照）
  - 共有シート非対応環境（主にPC）では、ボタン名は「Xでシェア」のまま、従来通り画像を先にダウンロードしてからXの投稿画面（新規タブ）を開く方式にフォールバックする。画像はクリップボード経由の自動貼り付けは試みず、常にダウンロードして投稿欄への手動添付を案内する（クリップボードコピーの信頼性とポップアップブロック回避が両立できなかったため、ダウンロード方式に一本化した経緯がある）
    - ダウンロードを投稿画面より先に行う理由：スマホでXのintent URLへ遷移するとネイティブアプリへ丸ごと切り替わりブラウザがバックグラウンドになるため、先に投稿画面を開いてしまうとダウンロードの確認ダイアログ等がユーザーの目に入らないまま放置され、画像が保存されずに終わる事例があった
  - ボタン下のヒント文言（「画像がダウンロードされ、投稿画面が開きます。投稿欄に添付してください」）は、フォールバック時（PC）のみ表示する。共有シートに委ねられる環境では、添付が自動で行われ宛先もXに限らないため、あえて出さない（共有シート自体が説明不要なUIであるため）
  - 添付画像があるとXのリンクカードが表示されないのはXの仕様上の正常な挙動と割り切り、共有シート経由でも「リンクカードを出す」ことは目的にしていない（URLはキャプション同様にただ渡すのみ）
- サービス公開ページ（`index.html`）にOGP／Twitter Card用のメタタグと専用のシェア画像（`public/ogp.png`）を用意し、URLをシェアした際にリンクカードとして表示されるようにしている（画像を添付しない共有・URLのみの共有では引き続き有効）
- 画像書き出し（PNG化）で使うWebフォントの埋め込みCSSは、プレビュー表示時に先読み・キャッシュしておき、「保存」「Xでシェア」ボタンをクリックした時点では再取得しないようにしている（詳細は7章参照。Google FontsのCJKサブセット分割の都合で、キャッシュなしだと1クリックごとに数百件規模のフォントファイル取得が発生し、体感速度に大きく影響していたため）

## 5. 入力フォーム仕様

- 年ごとにカード状のブロックで表示（年表のブロックと統一されたデザインテイスト）
- 各年カードの構成：
  - 年ラベル（黒背景の丸ピル等）
  - 入力済みの項目（ジャンル名＋カラースウォッチ＋削除ボタン）
  - 未入力の欄は常に1つだけ表示され、入力すると自動で次の欄が現れる（上限3、継続チップ込み）
  - 前年・翌年から続いている項目がある場合の「引き継ぎチップ」表示（双方向、詳細は3.5参照）
- カラー選択：5〜6色程度のスウォッチをタップで選択するシンプルなUI（複雑なカラーピッカーは使わない）
- 一言コメント欄は2行ぶんの高さを持つtextarea＋右下に文字数カウンター（例：12/30）を表示。1行のinputだと入力中に先頭が見えなくなる・上限がわかりにくいという課題があったため
- ヘッダーに「全部消す」ボタンを設置し、入力済みの年表データ（localStorage）を一括削除して初期状態に戻せる。確認ダイアログ（アプリのデザインに合わせた自前のモーダル。ブラウザ標準のconfirm()はURLが表示されてしまうため使わない）を挟み、誤操作による喪失を防ぐ

## 6. 見送った機能（将来の拡張候補）

以下は今回のMVPでは実装せず、必要になれば後日検討する。

  - MVPではシンプルなフォーム入力方式を採用
- **画像添付機能**（作品ごとに画像を付ける）
  - ビジーになりやすいため不採用。コメントのみ採用
- **色の自動提案機能**（似た項目名から過去に使った色を提案する）
  - シンプルさ優先で不採用。色は基本ランダム割り当て＋手動変更のみ
- **データのエクスポート／インポート機能、URL共有**
  - MVPではlocalStorageのみ

## 7. 検討の経緯（デザイン変遷メモ）

デザインは複数回のイテレーションを経て現在の形に落ち着いた。

1. 年バッジ＋作品チップ形式 → 年が目立ちすぎるとの指摘
2. サブウェイマップ風（ジャンルが線として主役）→ 方向性採用
3. 正方形固定＋ページ分割 → 「1枚の縦長画像」に変更
4. ミント背景＋シールデコ風 → 「白背景がよい」と方向転換
5. メンフィス風図形＋吹き出しバッジ → 吹き出しは不要、装飾はもう少し洗練させる方向に
6. コメントを専用列に配置 → ビジーで紐付けが分かりにくいとの指摘
7. コメントをハイブリッド配置（隣接／専用列の使い分け）→ それでも紐付けが分かりにくい
8. **最終形：コメントをブロック内部に内包**（タイトル＋小さい2行目）→ 採用
9. 配色をビビッド→パステルに変更、ブロックサイズ・行間を拡大、テキストを左上詰めに調整
10. 継続項目の引き継ぎチップを前年参照→翌年参照に変更。入力フォームは新しい年が上に並ぶため、上から順に埋めていくと前年参照では常に未入力のデータを見に行くことになり噛み合わなかった。翌年（すぐ上のカード）参照にすることで解消し、「＋もっと過去の年を追加する」で末尾に追加していく体験も変えずに済んだ
11. 継続入力チップを翌年参照のみ→前年・翌年の双方向に変更。上から新しい年順・下から古い年順のどちらで埋めても引き継ぎ候補が出るようにするための拡張。あわせて、同じジャンル名を持つ項目間でコメントを自動同期する機能を追加し、フィールド名も「作品名」→「ジャンル名」に変更（アニメ・ゲームに限らない趣味全般を扱うため）
12. ヘッダーに「全部消す」（全データリセット）機能を追加。動作確認・作り直しのたびにlocalStorageを手動でクリアする必要をなくすため。あわせて、シークレット／プライベートブラウジングで「画像として保存」が失敗する事例を調査。iOSのWeb Share API（`navigator.share`）はプライベートブラウジング中に`canShare`がtrueを返しつつ`share()`自体が拒否される既知の問題があるため、キャンセル以外の失敗時は通常のダウンロードに自動フォールバックするよう変更。あわせて、ダウンロード処理でBlob URLをclick()直後に同期的にrevokeしていた箇所も、ブラウザの読み込みより先にURLが無効化される競合を避けるため遅延させた
13. 「全部消す」の確認をブラウザ標準の`window.confirm()`から自前のモーダルダイアログに変更。`confirm()`は「（ホスト名）の内容」のようなユーザーに無関係な文言が必ず付き、デザインをコントロールできないため
14. 年表カードの横幅を固定600px→実使用レーン数（1〜3）に応じた可変幅に変更。レーンが1列しかないときに右側へ余分な余白が目立つとの指摘のため。レーンは1つあたり固定px幅とし、列数分だけカード全体の幅を伸縮させる。ただし見出し（タイトル＋年範囲バッジ）が窮屈にならないよう最小幅は維持する
15. 入力フォームの一言コメント欄を1行input→2行textarea＋文字数カウンター表示に変更。1行のままだと長めのコメント入力中に先頭が見えなくなる、上限文字数がわからず途中で入力できなくなって戸惑う、という指摘のため。任意項目としての圧迫感を避けるため、textareaの高さは2行までに留めた（自動拡張はしない）
16. 年表デザインを3点調整。(1)右上の年範囲バッジを廃止（年軸の年数字をフル表示にしたことで冗長になったため）(2)年軸の年数字を下2桁略記（'24）→4桁フル表示（2024）に変更し、フォントサイズ・色味も少し存在感を出す方向に調整 (3)フッター署名・Xシェアのデフォルトキャプションを、ハッシュタグ「#オタク年表メーカー」単体で完結させる形に変更（従来は「#オタク年表メーカーで作成」と地の文が繋がっており、サービス名そのもののハッシュタグとして検索しづらかったため）
17. 「Xでシェア」で投稿画面が about:blank のまま開かず、もう一度押すと開くという不具合を修正しようとした（一時的な変更）。空タブを先に開いてエクスポート完了後にURLを差し替える実装が、処理に時間がかかった場合にポップアップブロック判定に引っかかることがあると考え、`window.open()`自体をクリックハンドラの同期実行区間で確定URLを渡して直接呼ぶように変更した。しかし次の18で判明した副作用により、この変更は差し戻すことになった
18. 17の変更により、「Xでシェア」でクリップボードへの画像コピーが常に失敗するようになっていた（貼り付けても画像が出てこない）ことが判明し、17を差し戻して元の「空タブを先に開く」方式に戻した。原因：`navigator.clipboard.write()`はページがフォーカスを失うと`NotAllowedError: Document is not focused`で失敗する仕様があり、17の変更で実URL（X）へ即座に遷移するようにした結果、スマホではXのintent URLがネイティブアプリへの丸ごとの切り替えを引き起こし（ブラウザごとバックグラウンドになる）、その後のクリップボードコピーが確実に失敗するようになっていた。実URLへの遷移をクリップボードコピーの後に行う（＝17以前の順序）ことで、コピーの間はページのフォーカスが保たれるため解消した。17で心配していた「まれなポップアップブロック」よりも「クリップボードコピーが100%失敗する」方が実害が大きいと判断し、こちらを優先した
19. 18の方式に戻したところ、17で対処しようとしていた「投稿画面がabout:blankのまま開かない」不具合がやはり再発したため、根本的に方針転換した。クリップボードコピー（フォーカス維持が必須）と投稿画面を早く確実に開くこと（フォーカスを手放してよい）はそもそも両立しないと判断し、クリップボード経由の自動貼り付けを撤廃。画像は常にダウンロードし、投稿欄への添付は手動で案内する方式に一本化した。ダウンロードはフォーカス状態に依存しないため、投稿画面はユーザー操作直後に確定URLで直接開ける（17と同じ開き方だが、クリップボードを使わないため副作用が起きない）。あわせて、サービスの拡散のためXシェアのintent URLの`url`パラメータにサービス公開URLを付与するようにした
20. 19で「投稿画面を先に開く→画像をダウンロード」の順にしたところ、スマホの実機で「Xアプリへ遷移した後、画像が写真フォルダに保存されていない。ブラウザに戻るとダウンロード確認のダイアログが放置されていた」という報告があった。Xのintent URLへの遷移でブラウザごとバックグラウンドになり、その後に行うダウンロードの確認ダイアログ等をユーザーが見られないまま終わっていたと判明。ダウンロードとwindow.open()の順序を入れ替え、「画像をダウンロード→投稿画面を開く」に変更した。トレードオフとして、エクスポートに時間がかかった場合にwindow.open()自体がまれにポップアップブロックされる可能性が復活するが、その場合でも画像は既に保存済みのため、「画像が保存されないまま投稿画面だけ開く」場合より実害は小さいと判断した。あわせて、シェアされたURLがXでリンクカードとして表示されるよう、`index.html`にOGP／Twitter Cardのメタタグと専用画像（`public/ogp.png`、アプリの実際の見た目を模した1200×630のバナー）を追加した
21. 「画像として保存」「Xでシェア」のレスポンスが遅いという報告を受け、原因を調査。書き出し処理（`html-to-image`の`toBlob()`）はDOMをSVG化する際にWebフォント（Zen Maru Gothic / Zen Kaku Gothic New）をbase64で埋め込むが、この埋め込み処理は`@font-face`をフォントファミリー名だけでマッチさせ、実際に使われている文字（unicode-range）は見ていないことが判明。Google FontsはCJK対応のためこの2書体を大量のunicode-rangeサブセットファイルに分割して配信しており、実測でCSSレスポンスに729個の`@font-face`ルール（＝729個のフォントファイル）が含まれ、ボタンを押すたびに埋め込み処理がこれを丸ごと取得しようとしていた。年表で使うフォントファミリーはデータ内容に関わらず常に同じ（固定）で、事前に計算しておいて使い回すことに支障がないため、書き出し用の埋め込みCSSをプレビュー表示中に先読み・キャッシュし、ボタンクリック時は再取得せずキャッシュを再利用するよう変更した。2回目以降の書き出しはこのフォント取得コストがゼロになる（Playwrightでの検証では約9.5秒→66msに短縮）。初回の書き出しにかかるコストそのものは変わらないため、より根本的な対策（フォントを自前でサブセット化してローカルホストする等）は今後の検討課題として残す
22. 「Xでシェア」を、画像を添付するとX側の仕様でリンクカードが出ない、投稿欄への手動添付が必要、といった不満から方針転換。X限定ではなく`navigator.share()`によるOS標準の共有シート経由で画像・キャプション・URLをまとめて渡す方式に変更した（共有シートに画像ファイルを渡せる環境、主にスマホが対象）。共有シート経由なら添付が自動化され、宛先もX・LINE・Instagram・メールなど任意に選べる。これに伴いボタン名も、宛先がXとは限らないことが伝わるよう「Xでシェア」から「シェア」に変更した。ただしWeb Share APIはデスクトップブラウザでの対応にばらつきがあるため、`navigator.canShare({ files: [...] })`による機能検出で非対応と判定された環境（主にPC）では、ボタン名を「Xでシェア」のまま維持し、従来の「画像をダウンロード→Xの投稿画面を開く」方式にフォールバックする。あわせて、共有シート経由でもX上でのリンクカード表示は目的にしないことを明確化した（添付画像がある場合にカードが出ないのはX側の仕様として許容する）。ボタン下のヒント文言も、フォールバック時（PC）のみ表示するよう変更した（共有シートは説明不要なUIのため）
23. 22の方式をiOS×Chromeの実機で検証したところ、画像とキャプションはXの投稿画面に渡るものの、URLだけが本文に含まれないという不具合が報告された。調査の結果、`navigator.share()`に`files`と`url`を同時に渡すと、WebKit（iOS Safari／Chrome for iOSはいずれも内部的にWebKitを使用）では`url`が共有結果から欠落することがある既知の制約に該当すると判明（filesを渡す場合は他のフィールドの扱いが不安定になることがWebKit側で報告されている）。Androidの共有（Intent.ACTION_SEND）もそもそもtextとurlを別フィールドとして渡せず1本の文字列に結合される仕様であるため、いずれの環境でも「urlフィールドは信用せず、共有したい文字列は全てtextに含める」方が確実だと判断。`url`を独立したフィールドとして渡すのをやめ、キャプション文字列に`\n`区切りでURLを直接埋め込んで渡すように変更した
24. コメントの自動同期（3.6）と同様に、カラーも同じジャンル名を持つ項目間で同期して表示するよう変更した。それまではカラーが同期対象になっておらず、同じジャンル名でも年によって違う色になりうる状態だった。コメント同期のロジック（`commentSync.ts`）を拡張し、ファイル名も実態に合わせて`itemSync.ts`に変更。コメントとカラーで引き継ぎ方針を変えている点に注意：コメントは自由記述なので既存項目に何か入力されている場合のみ引き継ぐ（空なら上書きしない）が、カラーはジャンルの識別子的な位置づけのため、既存項目が見つかれば常にそちらの色に揃える（新規項目作成時にランダムで割り当てられた色を上書きする形になる）
25. 見出し「わたしのオタク年表」の「わたし」部分をユーザーが自由に設定できるようにした（例：「𓏸𓏸のオタク年表」）。プレビュー画面の書き出し対象（exportTargetRef）の外に「見出しの名前」という入力欄を新設し、そこに入力した表示名を見出しに反映する。書き出し対象の中に入力欄を置くと、入力欄自体が画像として書き出されてしまうため、外に配置する必要があった。表示名は年表データ（years）とは別のlocalStorageキーで保持し、次回訪問時も引き継がれる。最大文字数は6文字とした（見出しがカードの最小幅から1行ではみ出さない範囲を、実機描画で確認した上で決めた）。また、Xシェア時のデフォルトキャプション（「わたしのオタク年表 #オタク年表メーカー」）も見出しと同じ表示名を使うように変更し、見出しとシェア文言で呼び方が食い違わないようにした
26. 25で決めた表示名の最大文字数（6文字）が狭すぎるとの指摘を受け、10文字まで拡張した。文字数を増やすと見出しの横幅も伸びるため、それに合わせて年表カードの最小幅（`timelineLayout.ts`のMIN_CHART_WIDTH）も300→400に拡大した。ひらがな・カタカナ・半角英字それぞれ最大文字数いっぱいの表示名で見出しを実描画し、カードからはみ出さないことを確認した上で幅を決めている
