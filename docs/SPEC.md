# オタク年表メーカー 仕様書

自分がハマってきたものを年別に入力すると、1枚の年表画像を生成できるWebアプリ。生成した画像はXなどでシェアできる。

---

## 1. コンセプト

- 自分が今まで熱中してきたもの（作品・アイドル・趣味など）を年ごとに記録し、1枚の年表画像として可視化する
- 完成した画像はSNS（X）にシェアできる
- 簡単な作りで低コスト運用（サーバー不要、フロントエンドのみで完結）

---

## 2. 技術構成

| 項目             | 内容                                                                                     |
| ---------------- | ---------------------------------------------------------------------------------------- |
| フレームワーク   | React + Vite                                                                             |
| データ保存       | localStorageのみ（シンプル優先。エクスポート機能等は持たない）                           |
| デプロイ         | サーバー不要の静的ホスティングを想定（Vercel / Netlify等）                               |
| 画面構成         | 1画面完結型。入力とプレビューが同一画面上に並ぶ、リアルタイム連動更新                    |
| レスポンシブ対応 | PC：入力フォームとプレビューを左右並び<br>スマホ：「入力」「プレビュー」タブ切り替え表示 |
| アクセス解析     | Google Analytics（GA4、`index.html`にgtag.jsを直接埋め込み）                             |

## 3. データ仕様

### 3.1 年の範囲

- デフォルトで直近10年分を表示
- 「＋もっと過去の年を追加する」ボタンで、過去方向にどんどん年を追加できる
- 終了年（＝現在）は固定。開始年をユーザーに最初に入力させる負担は避ける

### 3.2 空欄の年の扱い

- **先頭側（一番古い側）の空欄**：年表画像から除外する（ノイズ削減）
- **途中の空欄**：そのまま表示する（時間軸の連続性を保つため）

### 3.3 1年あたりの項目数

- 最大3項目まで
- **継続項目も同じ3枠の中でカウントする**（別枠ではない）
  - 例：前年から2項目を引き継ぐと、新規入力できる欄は自動的に残り1つだけになる
  - 上限に達している場合は継続入力チップ自体が表示されない（エラー案内は出さず、UI側で自然に制限する）

### 3.4 各項目のデータ

| フィールド               | 必須/任意 | 文字数上限     | 備考                                                                                                                                                                                                                                                                                  |
| ------------------------ | --------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ハマったもの（タイトル） | 必須      | 20文字まで     | レーン幅を超える場合は折り返して複数行で全文表示（自動縮小はしない）。全角文字＋コメントの最悪ケースでもブロックからはみ出さないことを実描画で確認済み。アニメ・ゲームに限らず趣味全般を想定し、かつ書く粒度（ジャンル／作品／キャラ・カプ等）を限定しない名称にした（詳細は7章参照） |
| 一言コメント             | 任意      | 20〜30文字ほど | 画像は付けない方針。ブロック内にタイトルより小さい別カラーの2行目として表示。**同じジャンル名を持つ項目間ではコメントを自動同期する**（後述）                                                                                                                                         |
| カラー                   | 任意      | ―              | 未指定時はランダムで自動割り当て。ユーザーがスウォッチから手動で変更可能（自動提案機能なし）                                                                                                                                                                                          |

### 3.5 継続項目の入力サポート

- 継続入力チップは**双方向**に出す。前年（1つ下のカード）・翌年（1つ上のカード）のどちらに既存項目があっても、まだ未入力の年のドラフト枠にチップとして表示される
  - 前年からの継続は「昨年から：〇〇」、翌年からの継続は「翌年から：〇〇」とラベルで区別する
  - 上から新しい年順に埋める人・下から古い年順に埋める人のどちらの入力順にも対応するための変更（経緯は7章参照。当初は翌年参照のみの片方向だった）
- チップをタップすると同じ文字列・同じカラーがそのまま入力される（表記ゆれ防止）
- 年表側の「連続して線がつながる」表現は、**ジャンル名の完全一致**で判定する。この判定はチップの参照方向とは独立しており、どちらの年から先に入力してもタイトルが一致すれば連続ブロックになる
  - 例：「日プ」→「日プ2」→「日プ女子」のように表記が変わると、たとえ同じテーマでも別ブロックとして扱われる（同じ色を手動で選べば視覚的に揃えることは可能）

### 3.6 コメント・カラーの自動同期

- 同じジャンル名を持つ項目は、年をまたいでいても「同じ対象」とみなし、コメント・カラーの両方を自動で同期する
  - どこか1つの年でコメント・カラーを入力・編集すると、同じジャンル名を持つ他の年の項目にも即座に反映される
  - 継続入力チップから新規項目を作成した場合、既存の同名項目のコメント・カラーをそのまま引き継ぐ
  - 新規に手入力したジャンル名がすでに他の年で使われているものと完全一致した場合も、同様に引き継ぐ
- コメントとカラーで引き継ぎの扱いが少し異なる：コメントは自由記述のため既存項目にコメントがある場合のみ引き継ぐ（空なら上書きしない）が、カラーはジャンルの見た目上の識別子という位置づけのため、既存項目が見つかれば常にそちらの色に揃える（新規項目にはこの時点でランダムな色が割り当てられているだけなので、既存ジャンルの色で上書きする）
- 同期はジャンル名の完全一致で行うため、表記が変わると別項目として扱われ、コメント・カラーは引き継がれない（3.5と同じ判定基準）

## 4. 年表デザイン仕様

### 4.1 全体レイアウト

- 縦並びリスト型（上から下に時間が流れる）
- 生成画像は1枚に収める。ページ分割はせず、内容量に応じて縦方向に伸びていく可変長画像
- 高さ可変。横幅は、表示範囲内で実際に使われているレーン数（1〜3）に応じて自動で変わる
  - レーンが1列しかない場合に右側へ余分な余白ができるのを防ぐため
  - ただし見出し（タイトル）が窮屈にならないよう、最小幅は下限として維持する

### 4.2 年軸

- 左端に年の目盛り（小さいドット＋年数字）を配置
- 年数字は4桁フルで表示する（例：2024）。当初は下2桁の略記（'24）だったが、わかりやすさ・見た目の存在感を優先してフル表記に変更した
- 目盛りのドットは各年の**上端**に配置し、ジャンルブロックは「年と年の間」の空間に収まるように配置する

### 4.3 ジャンルブロック

- 白背景の上に、パステルカラーのブロック（角丸・薄い枠線・柔らかいドロップシャドウ）として表示
- レーン（列）は最大3列まで（年間の項目数上限と連動）。カード全体の横幅は実使用レーン数に連動する（詳細は4.1参照）
- 複数年にまたがって連続する項目は、線でつながって見えるように同色のブロックが縦に連続する
- ブロック内テキストは左上詰め
  - 1行目：ジャンル名（太字）
  - 2行目（コメントがある場合のみ）：一言コメント（小さめ・薄い色）
- 吹き出し風（しっぽ付き）の装飾は使わない
- ブロックはタップ／クリック可能。押すとその項目のコメント欄へジャンプする（詳細は5章・7章参照）。プレビューを見て気づいた修正のために毎回入力フォーム側で該当欄を探す手間を減らすための導線であり、書き出し対象（`exportTargetRef`）内の見た目自体は変えない（`cursor: pointer`やホバー時の明度変化はインタラクション時のみのCSSのため、書き出し画像には影響しない）

### 4.4 配色・雰囲気

- 背景は白
- ブロックの配色はパステル系（濃い原色は避ける）、全体的に柔らかい印象
- アクセントとして、線画のきらめき・リング・波線などのSVG装飾を控えめに散らす（メンフィス風の図形も参考にしつつ、やや洗練させたもの）

### 4.5 見出し・フッター

- 見出しは「（表示名）のオタク年表」の1行表示、傾き等の加工はしない
  - 表示名はプレビュー画面の書き出し対象の外にある入力欄（「見出しの名前」、最大10文字）で自由に設定できる。未入力時は「わたし」がデフォルトで、これまで通り「わたしのオタク年表」になる
  - 表示名はlocalStorageに年表データとは別キーで保存し、次回訪問時も引き継がれる
- 年の範囲バッジは表示しない（年軸に各年の年数字がフル表示されるため冗長と判断し廃止）
- 大きなブランドロゴ等は入れない（フッターに「#オタク年表メーカー で作成」と小さく署名程度）

### 4.6 シェア機能

- 「画像として保存」「シェア」（PCでは「Xに投稿する」）ボタンを設置
- シェア時は「（表示名）のオタク年表 #オタク年表メーカー」をデフォルトキャプションとして自動付与し、サービスの公開URLも一緒に渡す（投稿から辿ってアプリに来てもらうための拡散導線）。表示名は見出し（4.5参照）と同じ値を使い、呼び方が食い違わないようにしている
  - ハッシュタグはサービス名で検索しやすいよう「#オタク年表メーカー」単体で完結させ、後ろに文言を続けない（「#オタク年表メーカーで作成」のように地の文と繋げると別のタグになってしまうため）
- 「画像として保存」はiOSでは共有シート経由（Web Share API）を優先するが、シークレット／プライベートブラウジング中などでWeb Share自体が失敗するケースがあるため、その場合は通常のダウンロードに自動フォールバックする（ユーザーがキャンセルした場合を除く）
- 「シェア」は、モバイル端末（`isMobileDevice()`）かつOSの共有シートに画像ファイルを渡せる環境では`navigator.share()`でOS標準の共有シートを開き、画像・キャプション・URLをまとめて渡す。宛先はX限定ではなくユーザーが共有シートから選ぶ（詳細は7章参照）
  - URLは`url`フィールドとして独立させず、キャプション文字列（`text`）に直接埋め込んで渡す。`files`と`url`を同時に渡すと、iOS（WebKit）+ Xの組み合わせで実機検証した際にURLだけが共有結果から欠落することを確認したため（詳細は7章参照）
  - PC（デスクトップ）では、ボタン名を「Xに投稿する」にし、`navigator.share()`が機能的に使える場合であっても常に使わず、従来通り画像を先にダウンロードしてからXの投稿画面（新規タブ）を開く方式にする。PCのOS標準共有シートにはそもそもXが登録されていないことが多く、共有シートを開いても宛先候補にXが出てこないという実機報告を受け、機能検出だけでなく端末種別も見て判定するようにした（詳細は7章参照）。画像はクリップボード経由の自動貼り付けは試みず、常にダウンロードして投稿欄への手動添付を案内する（クリップボードコピーの信頼性とポップアップブロック回避が両立できなかったため、ダウンロード方式に一本化した経緯がある）
    - ダウンロードを投稿画面より先に行う理由：スマホでXのintent URLへ遷移するとネイティブアプリへ丸ごと切り替わりブラウザがバックグラウンドになるため、先に投稿画面を開いてしまうとダウンロードの確認ダイアログ等がユーザーの目に入らないまま放置され、画像が保存されずに終わる事例があった
  - ボタン下のヒント文言（「『Xに投稿する』は画像がダウンロードされ、投稿画面が開きます。投稿欄に添付してください」）は、共有シートを使わない場合（主にPC）のみ表示する。共有シートに委ねられる環境では、添付が自動で行われ宛先もXに限らないため、あえて出さない（共有シート自体が説明不要なUIであるため）
  - PC向けの投稿文（intent URLの`text`）には、通常のキャプション（`buildShareCaption`）に加えて「（画像はダウンロードされたものを添付してください）」という一言を含めて渡す。投稿画面に切り替わるとアプリ側のヒント文言が見えなくなり、添付を忘れたまま投稿してしまうことがあるという指摘を受けたため（詳細は7章参照）。モバイルの共有シート経由（`navigator.share()`）では画像が自動添付されるため、この一言は付けない
  - 添付画像があるとXのリンクカードが表示されないのはXの仕様上の正常な挙動と割り切り、共有シート経由でも「リンクカードを出す」ことは目的にしていない（URLはキャプション同様にただ渡すのみ）
- サービス公開ページ（`index.html`）にOGP／Twitter Card用のメタタグと専用のシェア画像（`public/ogp.png`）を用意し、URLをシェアした際にリンクカードとして表示されるようにしている（画像を添付しない共有・URLのみの共有では引き続き有効）
- 画像書き出し（PNG化）で使うWebフォントの埋め込みCSSは、プレビュー表示時に先読み・キャッシュしておき、「保存」「シェア」ボタンをクリックした時点では再取得しないようにしている（詳細は7章参照。Google FontsのCJKサブセット分割の都合で、キャッシュなしだと1クリックごとに数百件規模のフォントファイル取得が発生し、体感速度に大きく影響していたため）
- 「画像として保存」「シェア」が実際に完了した時点（クリックした時点ではなく、キャンセル・失敗した操作は含まない）で、GA4へそれぞれ`image_save`／`share`イベントを送る。完了した方式（`method`：`download`／`share_sheet`／`web_share`／`twitter_intent`）と、その時点で年表に入っている項目数（全年合計、`item_count`）をパラメータとして付与する（詳細は7章参照）

## 5. 入力フォーム仕様

- 年カード一覧の先頭に「クイック入力」欄（`QuickAddCard`）を常設する（詳細は7章参照）
  - 年の選択（プルダウン）＋「ハマったもの」入力＋「追加」ボタンの1行。年カードを上から順に埋める通常のフローとは別に、記憶が浮かんだ順にどの年へでも素早く追加できる手段を提供する
  - コメント・カラーはここでは扱わない（両方とも任意項目のため、まず「何に・いつハマったか」だけを次々書き留められることを優先し、連続入力のテンポを止めない）
  - 追加すると、その年のカードに項目が反映され、欄の下に「（年）年に「（内容）」を追加しました　コメント・色を編集 →」という確認メッセージが出る。リンクを押すとその項目のコメント欄までスムーズスクロール＋フォーカスする。押さなければクイック入力欄に留まり連続で追加を続けられる（追加のたびに強制スクロールはしない）
  - 対象の年が上限（3件）に達している場合は、追加を行わずエラーメッセージのみ表示する
  - 内部的には既存の年カードで新規項目を追加するのと同じ経路（`updateYearItems`）を通るため、同じタイトルの項目間のコメント・カラー自動同期（3.6参照）や継続入力チップ（3.5参照）もクイック入力経由の項目にそのまま適用される
- 年ごとにカード状のブロックで表示（年表のブロックと統一されたデザインテイスト）
- 各年カードの構成：
  - 年ラベル（黒背景の丸ピル等）
  - 入力済みの項目（ハマったもの＋カラースウォッチ＋「年を移動」「削除」ボタン）
  - 未入力の欄は常に1つだけ表示され、入力すると自動で次の欄が現れる（上限3、継続チップ込み）
  - 前年・翌年から続いている項目がある場合の「引き継ぎチップ」表示（双方向、詳細は3.5参照）
- 「年を移動」：間違えた年に入力してしまった項目を、削除して打ち直すことなく別の年へ動かせる（詳細は7章参照）
- プレビュー上のブロックをタップすると、入力タブへ自動で切り替わり（PCでは常に両パネルが見えているため見た目に影響しない）、該当項目のコメント欄までスムーズスクロール＋フォーカスする（詳細は4.3・7章参照）。クイック入力（`QuickAddCard`）の「コメント・色を編集 →」リンクと同じ`data-comment-for`属性を使ったジャンプの仕組みを再利用している
  - 「年を移動」を押すと、現在の年以外の年を選ぶプルダウンが現れ、選択すると即座に移動する（確認ボタンは挟まない。ネイティブのプルダウン操作自体が明確な選択行為のため）
  - タイトル・コメント・カラーはすべてそのまま移動先に引き継がれる（同名項目のコメント・カラー自動同期にもそのまま乗る）
  - 移動先の年が上限（3件）に達している場合は移動を行わず、その場にエラーメッセージのみ表示する
- カラー選択：5〜6色程度のスウォッチをタップで選択するシンプルなUI（複雑なカラーピッカーは使わない）。スウォッチの上に「カラー（同じ名前の項目は自動で揃います）」という一言ラベルを添え、何のための操作か・自動割り当てを手動で上書きできることを伝える（詳細は7章参照）
- 一言コメント欄は2行ぶんの高さを持つtextarea＋右下に文字数カウンター（例：12/30）を表示。1行のinputだと入力中に先頭が見えなくなる・上限がわかりにくいという課題があったため。プレースホルダーには「例：沼落ちした」と実例を1つ添え、何を書けばいいか分からず立ち止まってしまうのを防ぐ（詳細は7章参照）
- ヘッダーに「全部消す」ボタンを設置し、入力済みの年表データ（localStorage）を一括削除して初期状態に戻せる。確認ダイアログ（アプリのデザインに合わせた自前のモーダル。ブラウザ標準のconfirm()はURLが表示されてしまうため使わない）を挟み、誤操作による喪失を防ぐ
- ヘッダーのタグライン「ハマってきたものを年表画像に」は、PC以降ではタイトルと同じ行にインライン表示、スマホでは2行目のサブタイトルとして常時表示する（詳細は7章参照）
- ページ最下部にフッターを設置し、お問い合わせ用のGoogleフォームへのリンクと、プライバシーポリシーへのリンクを案内する（`Footer`コンポーネント。年表画像内のフッター署名とは別物）
  - プライバシーポリシーは`public/privacy.html`という、Reactアプリの外側にある素の静的HTMLとして用意している（このアプリはルーティングを持たないSPAで、1ページ増やすためだけにルーターを導入するほどでもないため）。Google Analytics（GA4）がCookieを利用してアクセス解析を行っている旨などを記載する
- 初回訪問時のみ、スポットライト式のチュートリアルオーバーレイを2ステップ表示する（`TutorialOverlay`コンポーネント。詳細は7章参照）
  - ステップ1：入力タブの入力エリア全体にスポットライトを当て、「ここから年表を作ろう」と案内
  - ステップ2：プレビューエリア全体にスポットライトを当て、「入力するとリアルタイムで反映」と案内（スマホでは「次へ」を押すと自動でプレビュータブに切り替わる）
  - ✕ボタンでいつでも終了でき、終了（✕、または最終ステップの完了）するとlocalStorageに記録され、次回以降は表示しない
- プレビューエリアがまだ何も入力されていない空の状態のときだけ、「こんな年表が作れます（サンプル）」という一言とともに完成イメージのサンプル画像を表示する（詳細は7章参照）
  - 既にOGP用に用意済みの`public/ogp.png`をそのまま流用しており、新規のアセット追加はしていない
  - 表示は書き出し対象（`exportTargetRef`）の外に置く。中に置くと、ユーザーが何も入力していない状態で「画像として保存」を押した場合に、サンプル画像ごと書き出されてしまうため（見出しの名前入力欄を外に置いているのと同じ理由）
  - 年ごとの項目を1件でも入力した時点で自動的に消える。ヘッダー画像等の常時表示物と異なり、役目を終えたら画面を占有し続けない

## 7. 検討の経緯（デザイン変遷メモ）

デザインは複数回のイテレーションを経て現在の形に落ち着いた。

1. 年バッジ＋作品チップ形式 → 年が目立ちすぎるとの指摘
2. サブウェイマップ風（ジャンルが線として主役）→ 方向性採用
3. 正方形固定＋ページ分割 → 「1枚の縦長画像」に変更
4. ミント背景＋シールデコ風 → 「白背景がよい」と方向転換
5. メンフィス風図形＋吹き出しバッジ → 吹き出しは不要、装飾はもう少し洗練させる方向に
6. コメントを専用列に配置 → ビジーで紐付けが分かりにくいとの指摘
7. コメントをハイブリッド配置（隣接／専用列の使い分け）→ それでも紐付けが分かりにくい
8. **最終形：コメントをブロック内部に内包**（タイトル＋小さい2行目）→ 採用
9. 配色をビビッド→パステルに変更、ブロックサイズ・行間を拡大、テキストを左上詰めに調整
10. 継続項目の引き継ぎチップを前年参照→翌年参照に変更。入力フォームは新しい年が上に並ぶため、上から順に埋めていくと前年参照では常に未入力のデータを見に行くことになり噛み合わなかった。翌年（すぐ上のカード）参照にすることで解消し、「＋もっと過去の年を追加する」で末尾に追加していく体験も変えずに済んだ
11. 継続入力チップを翌年参照のみ→前年・翌年の双方向に変更。上から新しい年順・下から古い年順のどちらで埋めても引き継ぎ候補が出るようにするための拡張。あわせて、同じジャンル名を持つ項目間でコメントを自動同期する機能を追加し、フィールド名も「作品名」→「ジャンル名」に変更（アニメ・ゲームに限らない趣味全般を扱うため）
12. ヘッダーに「全部消す」（全データリセット）機能を追加。動作確認・作り直しのたびにlocalStorageを手動でクリアする必要をなくすため。あわせて、シークレット／プライベートブラウジングで「画像として保存」が失敗する事例を調査。iOSのWeb Share API（`navigator.share`）はプライベートブラウジング中に`canShare`がtrueを返しつつ`share()`自体が拒否される既知の問題があるため、キャンセル以外の失敗時は通常のダウンロードに自動フォールバックするよう変更。あわせて、ダウンロード処理でBlob URLをclick()直後に同期的にrevokeしていた箇所も、ブラウザの読み込みより先にURLが無効化される競合を避けるため遅延させた
13. 「全部消す」の確認をブラウザ標準の`window.confirm()`から自前のモーダルダイアログに変更。`confirm()`は「（ホスト名）の内容」のようなユーザーに無関係な文言が必ず付き、デザインをコントロールできないため
14. 年表カードの横幅を固定600px→実使用レーン数（1〜3）に応じた可変幅に変更。レーンが1列しかないときに右側へ余分な余白が目立つとの指摘のため。レーンは1つあたり固定px幅とし、列数分だけカード全体の幅を伸縮させる。ただし見出し（タイトル＋年範囲バッジ）が窮屈にならないよう最小幅は維持する
15. 入力フォームの一言コメント欄を1行input→2行textarea＋文字数カウンター表示に変更。1行のままだと長めのコメント入力中に先頭が見えなくなる、上限文字数がわからず途中で入力できなくなって戸惑う、という指摘のため。任意項目としての圧迫感を避けるため、textareaの高さは2行までに留めた（自動拡張はしない）
16. 年表デザインを3点調整。(1)右上の年範囲バッジを廃止（年軸の年数字をフル表示にしたことで冗長になったため）(2)年軸の年数字を下2桁略記（'24）→4桁フル表示（2024）に変更し、フォントサイズ・色味も少し存在感を出す方向に調整 (3)フッター署名・Xシェアのデフォルトキャプションを、ハッシュタグ「#オタク年表メーカー」単体で完結させる形に変更（従来は「#オタク年表メーカーで作成」と地の文が繋がっており、サービス名そのもののハッシュタグとして検索しづらかったため）
17. 「Xでシェア」で投稿画面が about:blank のまま開かず、もう一度押すと開くという不具合を修正しようとした（一時的な変更）。空タブを先に開いてエクスポート完了後にURLを差し替える実装が、処理に時間がかかった場合にポップアップブロック判定に引っかかることがあると考え、`window.open()`自体をクリックハンドラの同期実行区間で確定URLを渡して直接呼ぶように変更した。しかし次の18で判明した副作用により、この変更は差し戻すことになった
18. 17の変更により、「Xでシェア」でクリップボードへの画像コピーが常に失敗するようになっていた（貼り付けても画像が出てこない）ことが判明し、17を差し戻して元の「空タブを先に開く」方式に戻した。原因：`navigator.clipboard.write()`はページがフォーカスを失うと`NotAllowedError: Document is not focused`で失敗する仕様があり、17の変更で実URL（X）へ即座に遷移するようにした結果、スマホではXのintent URLがネイティブアプリへの丸ごとの切り替えを引き起こし（ブラウザごとバックグラウンドになる）、その後のクリップボードコピーが確実に失敗するようになっていた。実URLへの遷移をクリップボードコピーの後に行う（＝17以前の順序）ことで、コピーの間はページのフォーカスが保たれるため解消した。17で心配していた「まれなポップアップブロック」よりも「クリップボードコピーが100%失敗する」方が実害が大きいと判断し、こちらを優先した
19. 18の方式に戻したところ、17で対処しようとしていた「投稿画面がabout:blankのまま開かない」不具合がやはり再発したため、根本的に方針転換した。クリップボードコピー（フォーカス維持が必須）と投稿画面を早く確実に開くこと（フォーカスを手放してよい）はそもそも両立しないと判断し、クリップボード経由の自動貼り付けを撤廃。画像は常にダウンロードし、投稿欄への添付は手動で案内する方式に一本化した。ダウンロードはフォーカス状態に依存しないため、投稿画面はユーザー操作直後に確定URLで直接開ける（17と同じ開き方だが、クリップボードを使わないため副作用が起きない）。あわせて、サービスの拡散のためXシェアのintent URLの`url`パラメータにサービス公開URLを付与するようにした
20. 19で「投稿画面を先に開く→画像をダウンロード」の順にしたところ、スマホの実機で「Xアプリへ遷移した後、画像が写真フォルダに保存されていない。ブラウザに戻るとダウンロード確認のダイアログが放置されていた」という報告があった。Xのintent URLへの遷移でブラウザごとバックグラウンドになり、その後に行うダウンロードの確認ダイアログ等をユーザーが見られないまま終わっていたと判明。ダウンロードとwindow.open()の順序を入れ替え、「画像をダウンロード→投稿画面を開く」に変更した。トレードオフとして、エクスポートに時間がかかった場合にwindow.open()自体がまれにポップアップブロックされる可能性が復活するが、その場合でも画像は既に保存済みのため、「画像が保存されないまま投稿画面だけ開く」場合より実害は小さいと判断した。あわせて、シェアされたURLがXでリンクカードとして表示されるよう、`index.html`にOGP／Twitter Cardのメタタグと専用画像（`public/ogp.png`、アプリの実際の見た目を模した1200×630のバナー）を追加した
21. 「画像として保存」「Xでシェア」のレスポンスが遅いという報告を受け、原因を調査。書き出し処理（`html-to-image`の`toBlob()`）はDOMをSVG化する際にWebフォント（Zen Maru Gothic / Zen Kaku Gothic New）をbase64で埋め込むが、この埋め込み処理は`@font-face`をフォントファミリー名だけでマッチさせ、実際に使われている文字（unicode-range）は見ていないことが判明。Google FontsはCJK対応のためこの2書体を大量のunicode-rangeサブセットファイルに分割して配信しており、実測でCSSレスポンスに729個の`@font-face`ルール（＝729個のフォントファイル）が含まれ、ボタンを押すたびに埋め込み処理がこれを丸ごと取得しようとしていた。年表で使うフォントファミリーはデータ内容に関わらず常に同じ（固定）で、事前に計算しておいて使い回すことに支障がないため、書き出し用の埋め込みCSSをプレビュー表示中に先読み・キャッシュし、ボタンクリック時は再取得せずキャッシュを再利用するよう変更した。2回目以降の書き出しはこのフォント取得コストがゼロになる（Playwrightでの検証では約9.5秒→66msに短縮）。初回の書き出しにかかるコストそのものは変わらないため、より根本的な対策（フォントを自前でサブセット化してローカルホストする等）は今後の検討課題として残す
22. 「Xでシェア」を、画像を添付するとX側の仕様でリンクカードが出ない、投稿欄への手動添付が必要、といった不満から方針転換。X限定ではなく`navigator.share()`によるOS標準の共有シート経由で画像・キャプション・URLをまとめて渡す方式に変更した（共有シートに画像ファイルを渡せる環境、主にスマホが対象）。共有シート経由なら添付が自動化され、宛先もX・LINE・Instagram・メールなど任意に選べる。これに伴いボタン名も、宛先がXとは限らないことが伝わるよう「Xでシェア」から「シェア」に変更した。ただしWeb Share APIはデスクトップブラウザでの対応にばらつきがあるため、`navigator.canShare({ files: [...] })`による機能検出で非対応と判定された環境（主にPC）では、ボタン名を「Xでシェア」のまま維持し、従来の「画像をダウンロード→Xの投稿画面を開く」方式にフォールバックする。あわせて、共有シート経由でもX上でのリンクカード表示は目的にしないことを明確化した（添付画像がある場合にカードが出ないのはX側の仕様として許容する）。ボタン下のヒント文言も、フォールバック時（PC）のみ表示するよう変更した（共有シートは説明不要なUIのため）
23. 22の方式をiOS×Chromeの実機で検証したところ、画像とキャプションはXの投稿画面に渡るものの、URLだけが本文に含まれないという不具合が報告された。調査の結果、`navigator.share()`に`files`と`url`を同時に渡すと、WebKit（iOS Safari／Chrome for iOSはいずれも内部的にWebKitを使用）では`url`が共有結果から欠落することがある既知の制約に該当すると判明（filesを渡す場合は他のフィールドの扱いが不安定になることがWebKit側で報告されている）。Androidの共有（Intent.ACTION_SEND）もそもそもtextとurlを別フィールドとして渡せず1本の文字列に結合される仕様であるため、いずれの環境でも「urlフィールドは信用せず、共有したい文字列は全てtextに含める」方が確実だと判断。`url`を独立したフィールドとして渡すのをやめ、キャプション文字列に`\n`区切りでURLを直接埋め込んで渡すように変更した
24. コメントの自動同期（3.6）と同様に、カラーも同じジャンル名を持つ項目間で同期して表示するよう変更した。それまではカラーが同期対象になっておらず、同じジャンル名でも年によって違う色になりうる状態だった。コメント同期のロジック（`commentSync.ts`）を拡張し、ファイル名も実態に合わせて`itemSync.ts`に変更。コメントとカラーで引き継ぎ方針を変えている点に注意：コメントは自由記述なので既存項目に何か入力されている場合のみ引き継ぐ（空なら上書きしない）が、カラーはジャンルの識別子的な位置づけのため、既存項目が見つかれば常にそちらの色に揃える（新規項目作成時にランダムで割り当てられた色を上書きする形になる）
25. 見出し「わたしのオタク年表」の「わたし」部分をユーザーが自由に設定できるようにした（例：「𓏸𓏸のオタク年表」）。プレビュー画面の書き出し対象（exportTargetRef）の外に「見出しの名前」という入力欄を新設し、そこに入力した表示名を見出しに反映する。書き出し対象の中に入力欄を置くと、入力欄自体が画像として書き出されてしまうため、外に配置する必要があった。表示名は年表データ（years）とは別のlocalStorageキーで保持し、次回訪問時も引き継がれる。最大文字数は6文字とした（見出しがカードの最小幅から1行ではみ出さない範囲を、実機描画で確認した上で決めた）。また、Xシェア時のデフォルトキャプション（「わたしのオタク年表 #オタク年表メーカー」）も見出しと同じ表示名を使うように変更し、見出しとシェア文言で呼び方が食い違わないようにした
26. 25で決めた表示名の最大文字数（6文字）が狭すぎるとの指摘を受け、10文字まで拡張した。文字数を増やすと見出しの横幅も伸びるため、それに合わせて年表カードの最小幅（`timelineLayout.ts`のMIN_CHART_WIDTH）も300→400に拡大した。ひらがな・カタカナ・半角英字それぞれ最大文字数いっぱいの表示名で見出しを実描画し、カードからはみ出さないことを確認した上で幅を決めている
27. 「見出しの名前」入力欄が小さすぎるとの指摘を受け、最大文字数（10文字）を入力しても入力欄内で文字が見切れないサイズまで拡幅した（w-24→w-56）。あわせて、お問い合わせ先として作成されたGoogleフォームへの案内をページ最下部のフッターに追加した（`Footer`コンポーネントを新設）。年表画像内のフッター署名（「#オタク年表メーカー で作成」）とは別物で、アプリのページ全体に対する案内として設置している
28. フッターの文言「〜からお気軽にどうぞ」を「〜まで」に簡潔化した。あわせて、Google Analytics（GA4、測定ID: G-RY0263PVXG）を導入した。`index.html`の`<head>`先頭付近（Google推奨の配置）にgtag.jsの標準スニペットを直接埋め込む形とした。SPAだがルーティングは行っておらず（タブ切り替えもURL変更を伴わないローカルstateでの表示切り替え）、ページ遷移が発生しないアプリのため、ページビュー計測用の追加コード（ルート変更検知など）は不要と判断した
29. GA4がCookieを利用してアクセス解析を行っている旨を告知するのが、日本国内の個人開発サイトでも一般的な定石（同意バナーまでは不要で、簡単な告知ページ＋フッターへのリンクという形が主流）と分かったため、プライバシーポリシーページを追加した。`public/privacy.html`という、Reactアプリの外側にある素の静的HTMLとして用意し、フッターにリンクを追加した。静的HTMLにした理由：このアプリはルーティングを持たないSPAで、1ページ増やすためだけにルーターを導入するほどでもないため。なお、開発時の検証で`vite dev`／`vite preview`はpublic/直下の追加.htmlファイルを正しく配信できず、SPA用のindex.htmlにフォールバックしてしまう既知の癖があると判明した（本番相当の挙動を確認するため、`dist/`をコピーしたディレクトリをPythonの素の静的サーバーで配信し、そちらで動作確認を行った）。GitHub Pagesのような素の静的ホスティングではファイルがそのまま配信されるため、本番では問題にならない
30. 公開に向けて、他の人が使う際にチュートリアル等の説明が必要かを検討した。フォーム入力＋即時プレビュー反映という一画面完結型のUIはそれ自体が説明を兼ねる設計になっており（プレースホルダー・空状態の案内文・シェアボタン下のヒント文言等）、別途チュートリアルを追加する必要はないと判断した。ただし実際の画面をスマホ幅で確認したところ、ヘッダーのタグライン「ハマってきたものを年表画像に」が`sm:block`指定によりスマホでは非表示になっており、スマホでの初回訪問時（デフォルトの「入力」タブ）にアプリの目的が一切説明されないまま入力欄だけが並ぶ状態になっていることが判明した。X等からの流入は大半がスマホだと想定されるため、この1点のみ修正：タグラインをPC以降は従来通りタイトルと同じ行にインライン表示し、スマホでは2行目のサブタイトルとして常時表示するようにした
31. 事前確認・ユーザーテストのチェックリスト（`docs/PRE_LAUNCH_CHECKLIST.md`）に基づき2名にユーザーテストを実施したところ、「開いた瞬間、何をしていいかわからない」という声が上がった。30で「別途チュートリアルは不要」と判断していたが、実際のユーザー行動としてその判断が覆ったため、初回訪問時のみ表示するスポットライト式チュートリアルを追加した（`TutorialOverlay`コンポーネント）。対象要素と同じ位置・サイズの透明な枠に非常に広い`box-shadow`を付けることで枠の外側だけを暗く見せる、定番のスポットライト表現を採用（SVGマスク等を使う複雑な実装は不要と判断）。クリックは全画面を覆う透明な層でブロックし、チュートリアル中は背後の要素を操作できないようにしている。ステップ1で入力エリア、ステップ2でプレビューエリアにスポットライトを当てる2ステップ構成とし、スマホでは「次へ」を押すと同時にタブもプレビューへ自動切り替えする（スマホは選択中タブしか表示されないため）。✕ボタンでいつでも終了でき、終了（✕、または最終ステップ「はじめる」の完了）すると`localStorage`に記録し、次回以降は表示しない。実装当初は説明の吹き出しを対象要素の直上・直下（`rect.top`／`rect.bottom`基準）に配置していたが、Playwrightでの動作確認中に、入力エリアのようにビューポートより縦に長いセクションを対象にした場合、吹き出しが画面外にはみ出して操作不能になる不具合が発覚した。対象の大きさによらず必ず画面内に収まる必要があるため、対象相対の配置をやめ、画面下部（`fixed inset-x-4 bottom-4`）に固定表示する方式に変更した（スポットライトと吹き出しが一部重なることはあるが、吹き出しは不透明・影付きで前面に出るため視認性は保たれる）

35. 34と同じユーザーテストで、「ハマったもの」入力後に現れる一言コメント欄・カラースウォッチについても「何を書けば／選べばいいか分からない」という声があった。原因を切り分けたところ、2つの異なる問題があると判断した。(1)コメント欄：既存のサンプル画像には「最終回で号泣した」等の実例が含まれているが、プレビューが空の状態でしか表示されない（32参照）ため、1件目の「ハマったもの」を入力した瞬間にサンプルごと消え、ユーザーがコメント欄に向き合う頃には手本が画面から無くなっているという、手当て済みの情報が届くタイミングのズレが原因と判断。プレースホルダーに「一言コメント（任意）」に加えて「例：沼落ちした」という実例を1行添えることで、粒度・書きぶりを書き手に委ねる方針は変えずに解消した。(2)カラースウォッチ：ラベルも説明も一切ないまま色ボタンが並んでいるだけだったため、素朴に「これは何」となっていたことに加え、「同じジャンル（例：ポケモンとモンハン）が別の色になるのは気持ち悪い」という、色を個別項目の同一性ではなくカテゴリのグルーピングとして使いたいという期待のズレも見つかった。後者について、ユーザーからは色に自由に名前を付けられるラベル機能＋年表内への凡例表示という提案があったが、(a)ラベル編集UI・保存スキーマ拡張・凡例描画と、このセッションで実装した他のどの機能よりも大掛かりであること、(b)色にこだわらない大多数のユーザーには新たな「これは何」を生みかねないこと、(c)「同じ色を意図的に選んで項目をグルーピングする」ということ自体は今の手動スウォッチ選択で既に実現できており、機能ではなく気づきの欠如が本質的な課題であること、の3点から実装を見送った。代わりにスウォッチの上に「カラー（同じ名前の項目は自動で揃います）」という一言ラベルを追加し、これが色を選ぶ場所であること・自動割り当てをタップで自由に上書きできることの両方を伝える形にした
36. ユーザーが手書きで作った参考シート（10年分の年表を、思い出した項目ごとに矢印で好きな場所に書き足していく形式）を見せてもらったところ、「2026年（今年）から降順で1年ずつ何にハマっていたか考えるのが難しい。コロナの時にモンハンにハマってたから2020年、のように記憶の方が先に浮かぶので、入力欄側に先に年を入力させてほしい」という指摘があった。年カード自体はどの年にも直接入力でき、上から順に埋める制約はもともと無いが、「まず年号を計算してから該当カードまでスクロールして探す」という2段階の手間が実質的な制約になっていたと判断。年カード一覧の先頭に「クイック入力」欄（`QuickAddCard`）を新設し、年の選択＋「ハマったもの」入力だけで、記憶が浮かんだ順にどの年へでも追加できるようにした。コメント・カラーは扱わない設計にした（任意項目のため、まず「何に・いつ」だけを連続して書き留められることを優先。手書きシートも思い出した項目をまず書き殴り、後から色や吹き出しで補足する2段階の使われ方に近い）。追加後は、確認メッセージ内の「コメント・色を編集 →」リンクを押した時だけ該当項目のコメント欄へスムーズスクロール＋フォーカスする設計にした。当初は追加のたびに自動でスクロールする案も検討したが、連続して次々に書き留めたいというクイック入力の本来の目的（思考のリズムを止めないこと）と相性が悪く、コメント・カラーはどのみち任意項目で後からいつでも追記できるため、能動的にリンクを押した場合のみジャンプする設計にした。内部実装は既存の`updateYearItems`（新規項目追加時の同名項目からのコメント・カラー自動引き継ぎを含む）をそのまま通す形にしたため、クイック入力経由の項目にも継続入力チップ（3.5）やコメント・カラー自動同期（3.6）がそのまま適用される。対象年が上限（3件）に達している場合は追加を行わずエラーメッセージのみ表示する
37. 36のクイック入力機能に関連して、「間違えた年に入力してしまった時、別の年に動かしたいが、今は一度削除して入力し直す必要があり手間」という指摘があった。削除→再入力だと、タイトルだけでなくコメント・カラーも失われてしまう（同名項目が他に無ければ引き継ぎ元も無いため）。ドラッグ＆ドロップでの並べ替えも検討したが、10年以上に渡る縦長のリストをスクロールしながらのドラッグ操作はモバイルでの実装・操作性のハードルが高く、このアプリの規模には過剰と判断し見送った。代わりに、各項目に「年を移動」ボタンを追加し、押すと現在の年以外を選べるプルダウンが現れ、選択すると即座にその年へ移動する方式にした（QuickAddCardの年選択と同じ発想）。実装は、移動元の年からの削除・移動先の年への追加をそれぞれ既存の`onChangeYearItems`（＝`updateYearItems`）で行うだけの単純な2段操作にした：`useState`の関数型更新はReactが呼び出し順に順次適用することを利用し、同一イベントハンドラ内で2回`onChangeYearItems`を呼んでも、2回目は1回目の更新が反映された状態から計算される。これにより、移動先の年に既に上限（3件）まで項目がある場合は移動を行わずエラー表示のみ行う、というガードも1箇所（`InputFormPanel`）に書くだけで済んだ。移動した項目のタイトル・コメント・カラーはオブジェクトごとそのまま移動先の年の配列に積むだけなので、`useTimelineData`側の新規項目引き継ぎロジックに一切手を入れずに済んでいる（同名項目が別途存在する場合は、そちらの色・コメントに揃うという既存の自動同期がそのまま働くのも意図通り）
38. 「プレビューを見て直したい箇所に気づいても、入力フォームに戻るのが面倒」という相談があった。プレビュー上で直接コメント・カラーを編集できるポップオーバーを検討したが、(a)書き出し対象（`exportTargetRef`）の外にポップオーバーを配置する実装、(b)モバイルでは縮小表示されるブロックへの正確なタップ操作、といった論点があり実装コストは中程度になると判断。まず低コストな案（プレビューのブロックをタップすると入力フォーム側の該当欄へジャンプするだけ）を試し、それでも「その場で完結させたい」という感覚が残るようなら本格的なポップオーバーに投資する、という段階的な進め方にした。実装は、クイック入力（36）の「コメント・色を編集 →」で使ったジャンプの仕組み（`data-comment-for`属性を目印にした`focus`＋`scrollIntoView`）をそのまま再利用：`TimelineChart`の各ブロックに`onItemClick`を渡すとタップ可能になり、`PreviewPanel`経由で`App`まで項目IDが渡ってくる。`App`側では、モバイルタブの切り替え（`setMobileTab('input')`）と直後にジャンプ先の項目IDをセットする状態更新を同じイベントハンドラ内で行い、`useEffect`でDOM検索を行うことで、タブ切り替え直後はまだ対象要素が`hidden`（display:none）で見つからない、という順序問題を避けている。ジャンプ先の状態は項目IDだけでなく`token`（実行のたびに変わる値）も持たせ、同じ項目を連続でタップしてもオブジェクト参照が変わって確実に`useEffect`が再実行されるようにした（stateを使い終えたらeffect内でnullに戻す、という実装も検討したが、oxlintの`set-state-in-effect`ルールに引っかかり不要な再レンダーを招くため見送った）。ブロックに追加した`cursor-pointer`やホバー時の明度変化はインタラクション時のみに適用されるCSSのため、書き出し画像（PNG）の見た目には影響しない。PCでは両パネルが常に表示されているためタブ切り替えは実質何もしないが、縦に長い入力欄一覧の中から該当項目まで自動でスクロール＋フォーカスされる点はPCでも変わらず有効に働く
39. 38の追加直後、「該当ブロックの一言コメント欄まで実際にフォーカスが当たった状態にしてほしい。近くの入力欄と見間違えることが多く、フォーカスまで当たっていればすぐ書き始められる」という指摘があった。原因は、38の実装がタブ切り替え後の`focus()`呼び出しを`useEffect`（タップのイベントハンドラから見て次のティック、非同期）で行っていたこと。モバイルブラウザ（特にiOS Safari）は、ユーザー操作の呼び出しスタックと直接つながっていない`.focus()`呼び出しに対して、`document.activeElement`は変更しても仮想キーボードは開かない・実質的にタップ操作からフォーカスが「地続き」に見えない、という制約があり、これが「フォーカスが当たっているように見えるのに近くの欄と見間違える」現象の原因と判断した。対処として、`useEffect`＋`jumpRequest`（itemId＋token）による非同期の仕組みを廃止し、`react-dom`の`flushSync`でタブ切り替えの状態更新を同期的にDOMへ反映させた直後、同じクリックハンドラ内で続けて`focus()`・`scrollIntoView()`を呼ぶ形に書き換えた。これによりタップ操作と同一の呼び出しスタック内でフォーカス処理が完結するようになった
40. 39の実機検証で、「フォーカスは当たるようになったが、その欄が仮想キーボードの下に隠れてパッと見つけられない」という報告があった。原因は、`focus()`直後に呼んでいる`scrollIntoView()`が、対象要素の位置を「仮想キーボードが出る前」のlayout viewport（`document.documentElement`のサイズ等）を基準に計算していること。iOS Safari等は、キーボード表示時にlayout viewport自体は縮小させず、実際に見えている範囲（visual viewport）だけを縮小させる挙動のため、`scrollIntoView()`はキーボードによる遮蔽を一切考慮できず、呼び直しても結果は変わらない。対処として、`visualViewport`の`resize`イベント（キーボード表示に伴う縮小）を検知したら、対象要素の位置と「実際に見えている範囲」（`visualViewport.offsetTop`＋`visualViewport.height`から算出した中心）とのズレを自前で計算し、そのズレの分だけ`window.scrollBy`で補正するようにした（`resize`が発火しない環境＝仮想キーボードが出ないPC等のフォールバックとして400msのタイムアウトも設定し、どちらか早い方で一度だけ実行）。Playwrightでは実機の仮想キーボード表示を再現できないため、`visualViewport.height`を疑似的に縮小して`resize`イベントを発火させるテストで、補正後に対象要素が「実際に見えている範囲」に収まることを確認した

GA4（28で導入済み）でアクセス解析ができるようになったことを受けて、「どのくらいの人が画像保存・シェアをしたか」をイベントとして計測したいという要望があった。既存の`gtag.js`スニペットにイベント送信を1行足すだけで実現できるため、新規ライブラリやスクリプトタグの追加は不要と判断。`image_save`／`share`イベントを、ボタンを押した瞬間ではなく処理が実際に完了した時点（キャンセル・失敗した操作は含まない）で送るようにした：`ShareButtons`の`handleSave`・`handleShare`はいずれも「共有シート成功」「ダウンロード成立」など複数の完了経路に分かれて既存の分岐があり、`trackEvent`の呼び出しをそれぞれの完了地点（`if (!saved) { downloadBlob(...) }`の直後、`navigator.share()`成功直後、PCフォールバックの`window.open()`直後）に個別に置くことで、キャンセル時（`AbortError`で`return`する経路）を自然に除外できた。あわせて、どの方式で完了したか（`method`：保存は`download`／`share_sheet`、シェアは`web_share`／`twitter_intent`）と、その時点で年表に入っていた項目数（`item_count`。全年の`items.length`合計。継続入力で見た目上つながって見えるブロックも、年ごとには別項目として数える）をパラメータに含めた。`window.gtag`はグローバル関数のため、`src/utils/analytics.ts`に`declare global`で型を補い、`trackEvent(name, params)`という薄いラッパーを1つ用意して呼び出し側の重複を避けた（広告ブロッカー等で`gtag.js`自体がブロックされ`window.gtag`が存在しない場合は何もしない）。動作確認は、Playwrightで`window.dataLayer.push`をラップして送信内容を検証する形にした：`index.html`のインラインスクリプトが`function gtag(){}`宣言で`window.gtag`を都度定義し直すため、`window.gtag`自体を直接差し替えるテストコードは上書きされてしまう。実際の`gtag()`は`dataLayer.push(arguments)`に委譲しているだけなので、`window.dataLayer`を先に用意して`push`をラップする方式にすることで、実装を変えずに送信内容を確実に捕捉できた

PC版の実機検証で、「シェア」ボタンを押すとWeb Share APIの共有先候補にXが出てこない、という報告があった。原因は、`shareFilesSupported`（現`shouldUseShareSheet`）を`canShareFiles()`（`navigator.canShare({files: [...]})`の機能検出）のみで判定していたこと。Web Share APIによるファイル共有はPCブラウザにも対応が広がってきており（22でこの機能検出方式を導入した時点のコメントで「PCブラウザでも将来対応が広がる可能性がある」と既に予見していた）、機能自体は使えても、PCのOS標準共有シートにはそもそもX（Twitter）が登録されていないことが多く、「シェアしたのにXが選べない」という体験になっていた。このアプリの「シェア」はXへの投稿を主目的としているため、機能検出だけでは不十分と判断。`src/utils/platform.ts`に`isMobileDevice()`（iOS判定の`isIOS()`に加えAndroidのUAも見る）を新設し、`canShareFiles() && isMobileDevice()`の両方を満たす場合のみ共有シート経由にするよう変更した。PCでは、`navigator.share()`が機能的に使える場合であっても常に使わず、ボタン名を「シェア」から明示的な「Xに投稿する」に変更した上で、従来からある「画像を先にダウンロードしてからXの投稿画面を新規タブで開く」方式（22・25等で構築済みのフォールバック経路）に固定した。画像は共有シートを介さないため自動添付されず、ボタン下のヒント文言（「投稿欄に添付してください」）による手動添付の案内は、この変更前から共有シート非対応環境向けに実装済みだったものがそのまま適用される形になり、追加の実装は不要だった。GA4イベント（41）の`method`パラメータ（`web_share`／`twitter_intent`）はコード分岐（実際に通った経路）ベースで送っているため、この変更による影響はない（PCでは`twitter_intent`に集約される）。動作確認は、PlaywrightでデスクトップUA＋`navigator.canShare`/`navigator.share`をモックしてtrueを返す環境（PCでも共有APIが機能する場合の再現）を用意し、ボタンが「Xに投稿する」と表示されること、クリック時に`navigator.share()`が呼ばれず`window.open()`でXのintent URLが開かれることを確認。あわせてAndroid UAの環境でも同様にモックし、ボタンが「シェア」と表示され`navigator.share()`が呼ばれることを確認した
43. PC版の実機検証で、「Xに投稿する」ボタンを押すと画像がダウンロードされ、Xの投稿画面が新規タブで開くところまでは確認できたが、「投稿画面に切り替わった後は、画像を投稿欄に手動で添付しないといけないことが伝わりづらい」という指摘があった。ボタン下にはヒント文言（42等参照）が既にあるが、投稿画面へ切り替わった時点でそのアプリ側の画面（別タブ／背後のタブ）は見えなくなるため、ヒントに気づけないまま投稿してしまう可能性があると判断した。対処として、PC向け投稿文（intent URLの`text`パラメータ）に、通常のキャプション（`buildShareCaption`）に加えて「（画像はダウンロードされたものを添付してください）」という一言を含める`buildTwitterIntentCaption`を新設し、この経路でのみ使うようにした。`buildShareCaption`自体は変更していない（モバイルの共有シート経由・`navigator.share()`では画像が自動添付されるため、この一言は不要かつ紛らわしいため）。`url`パラメータは従来通り独立させたまま変更していない（`text`に含めるべきなのはこの一言のみで、URL自体を`text`に埋め込む必要があるのはWeb Share API経由の共有（23参照）に限られるため）。動作確認は、Playwrightで`window.open`をラップしてintent URLをキャプチャし、`text`パラメータをデコードして一言が含まれていること、`url`パラメータが引き続き独立して正しく渡っていることを確認した
